Scriptorium — Comprehensive Consumer-Readiness AuditAudit date: 2026-09-17  Live GitHub HEAD audited: `01a23dd5ddb0091402bf8bb2601a44db29887f50`  Repository: `aryansinghnagar/Scriptorium`  Additional evidence: uploaded `7-Scriptorium.zip`  Audit focus: tangible defects, security vulnerabilities, data-integrity risks, reliability failures, packaging/distribution blockers, and consumer-readiness gaps. Preference/style nitpicks were intentionally excluded.1. Executive verdictRelease gate: BLOCKED.The project has a serious amount of hardening already in place, including shell quoting, fail-closed Typst installation, archive traversal checks, worker-threaded GUI execution, a broad regression harness, and CI execution. The September 17 re-audit is valuable historical evidence, but it predates the current `main` HEAD by five commits and therefore does not establish the current tree as consumer-ready.The most important current issue is a high-severity destructive restore-path bug: `restore_world.sh` sanitizes the user-supplied target name but never rejects an empty result. With `--force`, a target such as `!!!` becomes an empty string, producing `TARGET_FINAL_DIR="${DEST_PARENT}/"`; the script then executes `rm -rf` on the entire destination directory before restoring. This was reproduced safely in a disposable directory.There are also several important correctness and release-engineering problems:ambiguous project-name resolution can silently select the wrong world when duplicate names exist across universes;Debian and Flatpak launchers are packaged with the literal `__PROJECT_ROOT__` placeholder and therefore are not valid installed launchers;the `.gitignore` no longer ignores common secret/key files, increasing accidental credential-commit risk;the continuity engine attributes a trait assertion to every character present in a scene when the prose mentions more than one character, producing false contradiction reports;the GTK scene-metadata editor silently deletes supported/custom `@` tags it does not know how to rewrite;manuscript creation writes the author name directly into XML, so ordinary input such as `A & B` produces invalid `nwProject.nwx`;the installer returns success even when Obsidian/novelWriter/Calibre installation failed;Git initialization and commits during scaffolding are frequently swallowed with `|| true`, allowing “successful” projects without working initial history;repository branch protection is disabled despite project governance saying green CI is mandatory;packaging is not exercised by CI, so the broken launchers can regress without detection;the new `--fast` doctor path currently populates a cache but does not use cached results for the diagnostic analysis, so the claimed acceleration is not actually implemented.The uploaded ZIP itself also contains generated Python `__pycache__` artifacts and loses executable permissions in extraction, causing `tests/test_continuity_engine.sh` to fail when it directly executes `scripts/scriptorium`. This is not necessarily a Git-tree defect, but it is a distribution/reproducibility warning for ZIP-based delivery.2. FindingsH-01 — Restore `--force` can delete the entire destination directorySeverity: High  Category: Data loss / destructive command construction  Affected component: `scripts/restore_world.sh`Evidence:The requested target is sanitized with `tr -cd 'A-Za-z0-9_-'` and the result is not validated for emptiness.The final path is constructed as `DEST_PARENT/FINAL_WORLD_NAME`.`--force` performs `rm -rf "${TARGET_FINAL_DIR}"` if that path exists.Relevant source: `scripts/restore_world.sh:160-191`.Why this mattersA GUI or CLI user can enter a name consisting entirely of punctuation or other stripped characters, such as `!!!`. The sanitized result is empty. The resulting path becomes exactly the destination parent, and `--force` recursively removes it.ReproductionA disposable test created `/tmp/.../dest/KEEP/file`, restored a valid archive with `--target '!!!' --force`, and observed that `KEEP` disappeared before the archive was restored into the same directory.RemediationValidate the sanitized target name immediately after sanitization:reject empty;reject `.` and `..`;optionally require the result to equal a canonical safe token from the input rather than silently stripping most characters.Never allow `TARGET_FINAL_DIR` to equal `DEST_PARENT`.Resolve both paths with `realpath`/`readlink -f` and enforce `TARGET_FINAL_DIR` is a strict child of `DEST_PARENT`.Replace `rm -rf` overwrite semantics with a two-phase move-to-backup + atomic replacement strategy.Add a regression test for punctuation-only target names and a property test that asserts no destructive path can collapse to its parent.Acceptance testAny of `!!!`, `///`, `...`, whitespace-only, or non-ASCII-only target names must exit with a validation error before any filesystem mutation occurs.---H-02 — Ambiguous world names can silently operate on the wrong worldSeverity: High for data-integrity workflows; Medium from a security perspective  Category: Wrong-target selection / data corruption risk  Affected component: `scripts/lib/worlds.sh` and every caller using by-name world resolutionEvidence`resolve_world_dir` searches direct world paths in sorted filesystem order and returns the first directory whose basename equals the requested name. It does not reject ambiguity or require a universe when multiple matches exist.Relevant source: `scripts/lib/worlds.sh:165-218`.ReproductionWith:`~/Universes/U1/Shared``~/Universes/U2/Shared``resolve_world_dir Shared` returned `~/Universes/U1/Shared` without reporting ambiguity.ImpactThis is dangerous for commands that mutate data or produce authoritative artifacts: snapshotting, backup, export, diagnostics, concordance generation, and legacy compatibility paths can act on the wrong project without an obvious error. For authors with multiple universes, duplicate world names are realistic rather than exotic.RemediationMake by-name resolution return one of: exact path, exactly one match, or explicit ambiguity failure.Add `--universe` as mandatory when multiple matches exist.In GUI selectors, always carry the full absolute path or stable project identifier rather than resolving again from the basename.Add a `resolve_world_dir --strict` mode and make destructive/mutating commands use strict mode unconditionally.Apply the same rule to manuscript-name collisions.---M-01 — Debian and Flatpak desktop launchers are not installable as shippedSeverity: Medium  Category: Packaging / consumer installation failure  Affected component: `launchers/*.desktop`, `debian/rules`, `org.scriptorium.Scriptorium.yaml`EvidenceThe launcher files contain:`Exec=bash "__PROJECT_ROOT__/scripts/..."`The setup installer replaces `__PROJECT_ROOT__`, but the Debian and Flatpak packaging rules simply copy the `.desktop` files without substitution.Relevant source: launcher files; `debian/rules:25-29`; `org.scriptorium.Scriptorium.yaml:23-32`.ImpactA repository-installed setup can work, while a packaged `.deb` or Flatpak installation can place broken application-menu/desktop launchers on the user's system. This is a direct consumer-facing packaging failure.RemediationChoose one packaging-safe strategy and use it everywhere:Debian: hard-code `/usr/share/scriptorium/scripts/<entry>.sh` into package-specific desktop files generated during build, or install wrapper binaries in `/usr/bin` and make `.desktop` entries call those wrappers.Flatpak: use `/app/bin/<command>` as the executable path.Do not make package launchers depend on a source-tree placeholder.Add CI that builds both package formats and validates the resulting installed launcher `Exec=` paths.---M-02 — Secret-file protections were removed from the root `.gitignore`Severity: Medium  Category: Credential leakage / repository hygiene  **EvidenceThe current `.gitignore` includes Python caches, backups, archives, etc., but no longer ignores `.env`, `.pem`, `.key`, or `.cert` files. The current commit explicitly replaced those patterns with cache/package-artifact ignores.Relevant source: root `.gitignore`; current `main` diff.ImpactScriptorium itself is local-first and currently has no cloud secrets, but contributors, CI experiments, packaging credentials, signing keys, or external integration tests may create these files. Removing the protections increases the probability of accidental credential commits.RemediationRestore broad accidental-secret patterns, for example:`.env``.env.*``*.pem``*.key``*.cert``*.p12``*.pfx`Then add a real secret scanner to CI (for example Gitleaks or equivalent), plus repository history scanning before public release.---M-03 — Continuity engine can attribute one character's trait to anotherSeverity: Medium  Category: Incorrect diagnostics / trust erosion  Affected component: `scripts/lib/continuity.py`EvidenceWhen no scene tags identify the active cast, the engine adds every known character whose name appears anywhere in the full scene text. It then applies every trait assertion on every line to every character in that scene.Relevant source: `scripts/lib/continuity.py`.ReproductionA scene containing:`Alice and Bob stood by the gate. Bob looked into Alice's green eyes.`produced a contradiction for Bob's eye color even though the green eyes belong to Alice.ImpactAs the manuscript becomes more complex, the engine can produce false positives at a high rate. Authors will eventually learn to ignore continuity warnings, which defeats the feature's purpose.RemediationMove from scene-level attribution to sentence/mention-level attribution.Resolve character mention spans before assigning traits.Prefer explicit metadata (`@char`, `@pov`) as high-confidence context.Treat pronouns and possessives conservatively; do not emit a contradiction when ownership is ambiguous.Introduce confidence scores and only elevate high-confidence contradictions.Add adversarial fixtures with two, five, and ten characters in a scene.---M-04 — GTK scene metadata editing silently deletes custom `@` tagsSeverity: Medium  Category: Data loss  Affected component: `scripts/lib/ui_gtk3.py`EvidenceThe metadata editor strips a hard-coded set of tags (`@pov`, `@char`, `@location`, `@thread`, `@time`, `@status`, etc.) and rewrites only those fields. Other supported/custom tags are not preserved. In particular, the code strips `@tag:` but does not re-create it; arbitrary tags such as `@theme`, `@object`, or user-defined tags are preserved neither as metadata nor as prose.Relevant source: `scripts/lib/ui_gtk3.py:967-1045`.ImpactOpening a scene and saving metadata can silently alter author-authored metadata. This is unacceptable for a consumer authoring tool whose primary data is plain text.RemediationParse metadata into an ordered tag model.Update only fields the user explicitly changed.Preserve all unknown tags byte-for-byte where possible.Preserve tag order/comments unless the user explicitly normalizes them.Add a round-trip test: load → edit known field → save → assert every unrelated byte is preserved.Perform atomic file replacement and create an automatic pre-edit snapshot for this specific operation.---M-05 — User-supplied author names can generate invalid novelWriter XMLSeverity: Medium  Category: Data corruption / first-run failure  Affected component: `scripts/init_manuscript.sh`Evidence`AUTHOR_NAME` is interpolated directly into `<author>...</author>` without XML escaping.Relevant source: `scripts/init_manuscript.sh:158-165`.ReproductionCreating a manuscript with `--author 'A & B'` generated:`<author>A & B</author>`which fails XML parsing with `invalid token`.RemediationGenerate XML with a real XML writer or escape `& < > " '` correctly for element text/attributes.Validate the generated `.nwx` immediately after creation.Add fixtures for `A & B`, `O'Connor`, `Müller`, emoji, quotes, and newline-containing input.Do the same audit for every generated YAML/XML/Typst artifact.---M-06 — Installer reports success when required Flatpak applications failed to installSeverity: Medium  Category: Installation reliability / false success  Affected component: `scripts/setup_scriptorium.sh`Evidence`flatpak_install` returns exit code 0 even after both system and user installation attempts fail, printing only a notice that installation was skipped.Relevant source: `scripts/setup_scriptorium.sh:186-208`.ImpactThe installer can finish with `[SUCCESS]` while a new user is missing Obsidian, novelWriter, or Calibre. The UI and workflow documentation present these applications as installed components.RemediationTreat required authoring applications as hard failures.Track per-component state and return a non-zero code when a declared required dependency is unavailable.Distinguish `already installed`, `installed`, and `failed`.Produce a machine-readable install report.Make optional tools explicit rather than silently skipping them.---M-07 — Project bootstrap can claim Git integration succeeded after Git operations failedSeverity: Medium  Category: Reliability / false assurance  Affected components: `init_universe.sh`, `init_world.sh`, `init_manuscript.sh`, `add_book.sh`EvidenceSeveral initial `git add`/`git commit` operations are guarded by `|| true`, after which the scaffold continues and reports successful Git initialization.Relevant example: `scripts/init_manuscript.sh:222-244`.ImpactA project can be created with missing initial commits or incomplete staging while the user is told Git version control was initialized. The failure may only surface later during snapshots or recovery.RemediationTreat repository initialization and first commit as part of the transaction when Git is available.If Git is optional, report `created without version history` explicitly.If Git is required by product guarantees, fail the scaffold when Git setup fails.Return a distinct diagnostic code and explain how to repair it.---M-08 — CI quality gate is not actually enforced by branch protectionSeverity: Medium  Category: Release governance  **EvidenceThe live `main` branch metadata reports `protected: false`, with required status checks disabled, even though project governance says green CI on pull requests is mandatory.ImpactA failing build or security regression can be merged directly into `main`. That makes claims such as “CI is mandatory” operationally false.RemediationProtect `main`.Require the CI workflow as a status check.Require pull requests and at least one approval once collaborators exist.Disable force-pushes and branch deletion.Require linear history only if the project workflow benefits from it; avoid introducing policy without operational need.Add CODEOWNERS for security-sensitive scripts once a maintainer set exists.---M-09 — Packaging is outside the CI verification boundarySeverity: Medium  Category: Release quality / untested distribution pathThe current CI validates shell/Python syntax, configuration, the verification harness, regression tests, Typst, and Pandoc, but it does not build and install-test the Debian or Flatpak artifacts that the current branch has added.The modernization documentation itself lists packaging build/lint checks as an acceptance item, but the workflow does not implement them.ImpactThe broken `__PROJECT_ROOT__` launcher defect can coexist with green CI.RemediationCI should have dedicated jobs for:`dpkg-buildpackage` / `dpkg-deb` build;`lintian` package analysis;install package into a clean Debian/Ubuntu test VM/container;validate desktop files after installation;build Flatpak with `flatpak-builder`;install/run the Flatpak in a headless smoke environment;execute CLI and launcher path tests from the installed filesystem, not from the source tree.---M-10 — Restore integrity is not authenticitySeverity: Medium in distributed-backup scenarios  Category: Backup trust modelRestore verifies a `.sha256` sidecar when present, but explicitly accepts archives without one and acknowledges that the sidecar can be replaced by whoever replaces the archive.This is acceptable as a corruption check, but not as a trust boundary for downloaded/shared backups.RemediationMake a missing integrity manifest a failure for normal restore.Version the backup format and include a manifest of all expected files.For portable backup sharing, support an optional signed manifest or detached signature.Clearly label SHA-256 as “integrity against accidental corruption,” not authenticity.---L-01 — `--fast` doctor mode does not actually use cached diagnostic resultsSeverity: Low/Medium  Category: Performance / misleading optimization`world_doctor.sh --fast` invokes `cache.scan_project(...)` and then performs its normal analysis logic. There is no code path that consumes the indexed cache to avoid the expensive file scanning/parsing.Relevant source: `scripts/world_doctor.sh:147-155`.ImpactThe cache is currently an additional I/O operation rather than a real acceleration layer for doctor analysis.RemediationRefactor the doctor engine around a reusable indexed document model. Standard mode should build the index from scratch; fast mode should consume valid cache entries and only reparse invalidated files.---L-02 — Cache parsing errors are swallowed and represented as zero-ish dataSeverity: Low/Medium  Category: Diagnostic correctness`cache.py` catches read/parse exceptions and records an error entry, while scan traversal also suppresses exceptions. Consumers can therefore receive incomplete indexed state without an explicit failed operation.RemediationExpose cache health separately from result data, fail the fast path closed when index integrity is uncertain, and fall back explicitly to a full scan with an observable warning.---L-03 — Current quality documentation overstates the regression-harness pictureSeverity: Low  Category: Documentation trustworthinessThe current repository contains six `tests/*.sh` suites, including the new continuity and performance suites, while README/knowledge-base text still describes five suites. The canonical `verify.sh` is also not itself a wrapper for every regression suite; CI runs the test scripts separately.RemediationMaintain a single generated test inventory and report it in README/CI output so documentation cannot drift from the actual suite.---L-04 — Uploaded ZIP is not a clean reproducible release artifactSeverity: Low  Category: Distribution hygieneThe uploaded ZIP contains Python `__pycache__` artifacts and legacy `docs/meta/*` material that does not match the cleaned live-main tree. It also did not preserve executable permissions in the extracted workspace.RemediationCreate release archives directly from tagged Git commits; never distribute arbitrary working-directory ZIPs. Add a release artifact manifest and reproducibility check.4. Positive controls worth preservingThe audit is not a rewrite recommendation. Several existing controls are valuable and should remain foundational:quoted shell arguments and `set -euo pipefail` throughout the core scripts;NUL-delimited filesystem enumeration in the shared discovery library;fail-closed Typst digest validation;archive traversal and Git-hook checks before restore extraction;temporary staging with cleanup traps for creation/restore flows;subprocess execution with argument arrays rather than shell interpolation;GUI background workers with GTK main-thread marshaling;SHA-256 backup manifests;a broad sandboxed integration harness;pinned GitHub Action SHAs and a least-privilege CI permissions block.These are good foundations; the next phase should tighten correctness around them rather than adding more surface area.5. Consumer-readiness remediation programPhase 0 — Immediate safety gateMust be completed before any wider distribution.Fix H-01 restore path validation.Make world/manuscript resolution ambiguity-failing.Add destructive-operation dry-run previews.Add regression tests for punctuation-only names, duplicate names, and `--force` restores.Re-run the full test suite from both a Git as source-tree execution.Phase 3 — Security and release governanceRestore secret patterns in `.gitignore`.Add a secret scanner.Protect `main` and require CI.Add dependency drift monitoring for APT/Flatpak/package tooling.Define a release-signing model for `.deb`, Flatpak repository metadata, and portable backups.Publish a supported-version policy tied to actual released versions, not only Definition of consumer-readyI would require all of the following before changing the public status from development/audit-verified to genuine consumer-ready:No High findings.No data-loss Medium findings.Duplicate project names always resolve deterministically or fail closed.Every destructive operation has a safe preview and a tested confirmation boundary.`.deb` and Flatpak packages are actually built, installed, and smoke-tested in CI.`main` cannot merge without the required CI result.Release artifacts are versioned, checksummed, and reproducible from a tag.Generated Markdown/YAML/XML survives arbitrary normal user input.GUI metadata editing is lossless for unknown metadata.Continuity diagnostics demonstrate high-confidence behavior on multi-character scenes.Backup/restore tests cover corrupted archives, missing manifests, malicious members, symlinks, duplicate roots, invalid target names, existing targets, and cross-version restores.The user-visible success state is always coupled to the real process exit status.The project can be installed from a release artifact without cloning the source repository or relying on repository-specific placeholders.7. Recommended implementation orderThe shortest path to a robust consumer release is:Restore safety → strict path resolution → lossless file editing → manifest escaping → installer fail-closed behavior → packaging launchers → package CI → branch protection → secret scanning → continuity correctness → real cache integration → release automation.The project does not need a wholesale rewrite. Most of the current architecture can remain. The highest-value work is enforcing stronger invariants at the boundaries where user input becomes filesystem paths, generated documents, packaged launchers, or automated diagnostics.8.
