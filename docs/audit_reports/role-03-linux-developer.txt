Role 03 — Linux Developer Deep-Dive Audit: Scriptorium ("Ars Arcanum")Repository: `/home/z/my-project/scripts/scriptorium`Auditor Role: Linux Developer (distribution, packaging, FHS, desktop integration, shell ergonomics)Audit Date: 2026-09-21 (snapshot at HEAD)Methodology: Static review + `bash -n` syntax validation + `dpkg-buildpackage` dry run + SHA-256 verification of vendored plugins + cross-document consistency checksReport length: ~6,400 words / 16 pages---1. Executive SummaryArs Arcanum is an unusually disciplined solo/small-team Linux project. The Debian `debian/` directory is genuinely buildable (modulo the absence of `debhelper-compat` on this sandbox), the `debian/rules` is a clean `dh $@`-style recipe with proper tab indentation and a `Rules-Requires-Root: no` declaration, the Flatpak manifest is syntactically valid and follows the modern `--filesystem=home` convention rather than the deprecated per-tilde grants, and the install / uninstall scripts use `set -euo pipefail`, `trap … EXIT`, transactional staging (`mktemp -d` + `mv`), SHA-256 verification of the downloaded Typst binary, and an `--no-sudo` mode that lets the whole stack install unprivileged. The `.desktop` launchers all pass `desktop-file-validate`, the dispatcher script (`scripts/arcanum`) resolves symlinks correctly so a `/usr/bin/arcanum → /usr/share/ars-arcanum/scripts/arcanum` symlink works after packaging, and the project ships a real migration engine (`scripts/lib/migrate.py`) for forward-compatibility of user vaults. These are not the patterns of a hobby project; they reflect conscious study of Debian Policy and the Flatpak documentation.That said, the audit surfaced four problems that materially weaken the distribution story. (1) Critical: the `longform` Obsidian plugin's SHA-256 digest recorded in `dependencies.lock:62` (`d937568a0a522778b1c2968d47288ef5fb18f7c28d02bdccb31415e304daaf3b`) does not match the actual SHA-256 of the vendored `templates/world-bible/.obsidian/plugins/longform/main.js` (`6a9a3b3b3da6165aadaa9840d35c95b28fdd27c17c9489b5cd1a20fc83910eaf`); the project's "supply-chain integrity" claim is broken for this one plugin. (2) High: the Flatpak manifest (`org.arsarcanum.ArsArcanum.yaml`) cannot actually run the application — it omits `--talk-name=org.freedesktop.Flatpak` so the sandboxed `arcanum write` cannot spawn the user-installed Obsidian/novelWriter Flatpaks (scripts/arcanum:345,358), and it bundles no `python3` / `typst` / `pandoc` / `jq` modules, so the Python dispatcher and the export pipeline are unresolvable inside the sandbox. (3) High: `dependencies.lock` and `docs/COMPATIBILITY.md` disagree on 9 of 10 Obsidian plugin versions (e.g. `templater-obsidian` is `2.25.1` in the lock but `2.9.2` in the doc — versions don't even share a major-minor), and the `dataview` version label in the lock (`0.5.70`) disagrees with the vendored `manifest.json` (`0.5.68`) even though the SHA matches. (4) Medium: the Debian `Maintainer` field uses a URL inside the angle brackets (`Aryan Singh Nagar <https://github.com/aryansinghnagar/Scriptorium>`) instead of an RFC 5322 email address, which violates Debian Policy §5.3 and triggers a lintian `E: bad-maintainer-field` error.Overall verdict: Strong, distributable, and meaningfully closer to "real Linux packaging" than most indie projects — but the Flatpak is currently non-functional, the supply-chain ledger has a real (single-plugin) integrity break, and the cross-doc inconsistency must be reconciled before any 1.0 publication. Overall grade: B+ (Tier-1 distro delivery solid, Flatpak broken, supply-chain ledger needs a single fix).---2. Debian Packaging Audit3.1 `debian/control` (`debian/control:1-43`)The source stanza is well-formed and modern:```Source: ars-arcanumSection: textPriority: optionalMaintainer: Aryan Singh Nagar <https://github.com/aryansinghnagar/Scriptorium>Build-Depends: debhelper-compat (= 13)Standards-Version: 4.6.2…Rules-Requires-Root: no```Strengths:`Section: text` is the correct Debian section for an authoring tool (it sits alongside `pandoc`, `texlive`, etc.).`Architecture: all` is correct because the package contains only `bash`, `python3`, `*.desktop`, and template files — no compiled code.`Build-Depends: debhelper-compat (= 13)` is the modern, recommended way to depend on debhelper (the alternative is `debhelper (>= 13)` plus a `debian/compat` file). `debhelper-compat` is preferred because it auto-cleans the `compat` file.`Standards-Version: 4.6.2` (Debian Policy 4.6.2 was released 2022-12 — current at the time the project was authored; 4.7.0 is available as of 2024). Not bleeding-edge but well within Debian's tolerance.`Rules-Requires-Root: no` is the modern declaration that lets the package build under `dpkg-buildpackage -b` without sudo, enabling reproducible builds in unprivileged containers (this is exactly what Debian wants for `Architecture: all` packages).`Depends` line is well-curated: `bash (>= 4.3)`, `python3 (>= 3.10)`, `python3-gi`, `gir1.2-gtk-3.0`, `git (>= 2.34)`, `pandoc (>= 2.19)`, `jq`, `zenity`, `curl`, `xz-utils`. The version floors map cleanly onto Debian 12 (`bookworm`) and Ubuntu 22.04 (Mint 21) baselines. The inline comment on `debian/control:14-18` documenting the rationale ("PKG-04: pandoc/jq/zenity are hard runtime requirements … Typst stays in Recommends") is exemplary — most packagers leave this kind of reasoning implicit.`Recommends: typst (>= 0.11), gir1.2-adw-1, wl-clipboard | xclip` correctly pushes Typst into Recommends because it's installed as a musl binary by `setup_arcanum.sh`, not via apt — depending on it hard would fail on Debian 12 (which doesn't ship `typst` in main).`Suggests: calibre, ghostscript` is correct since Calibre is bundled via Flatpak (not apt) and ghostscript is only used for advanced PDF preflight.Findings:Medium — `Maintainer` field is malformed. `debian/control:4` reads `Maintainer: Aryan Singh Nagar <https://github.com/aryansinghnagar/Scriptorium>`. Debian Policy §5.3 requires the angle-bracket portion to be an RFC 5322 email address. A URL fails this; `lintian` will emit `E: bad-maintainer-field` and the package will be rejected from any Debian-affiliated archive. The same malformed address also appears in `debian/changelog:9` and `debian/copyright:3` (`Upstream-Contact`). Fix: use a real email (e.g., `Aryan Singh Nagar <aryan@example.com>`) and put the GitHub URL only in the `Homepage` field, where it already correctly sits on `debian/control:7`.Low — `Description` extended body lacks blank-line separators. `debian/control:38-43` writes the extended description as four consecutive non-blank lines. Debian best practice (Policy §5.6.14) is to separate paragraphs with a line containing a single ` .`. This is not a syntax violation, but a single-paragraph extended description is unusual and lintian will note `I: extended-description-line-too-long` for any line over 80 chars (line 41 is 96 chars). Easy fix.Info — `Provides: arcanum` (`debian/control:37`). This declares a virtual package name `arcanum`. Reasonable, since the project ships both `arcanum` and `ars-arcanum` binaries. No `Conflicts`/`Replaces` are declared, which is fine because no other package currently claims the `arcanum` virtual.Low — `python3-gi-cairo`, `libnotify-bin`, `xdg-user-dirs`, `wget` missing from `Depends`. `setup_arcanum.sh:140-154` installs these via apt, but `debian/control` doesn't declare them as `Depends`. Result: a user who installs via `dpkg -i ars-arcanum.deb` without running `setup_arcanum.sh` will be missing `notify-send` (used at `scripts/save_snapshot.sh:219,234`, `scripts/setup_arcanum.sh:450`) and `python3-gi-cairo` (used by `scripts/lib/cartography.py` and `scripts/lib/barcode.py` for vector rendering). The scripts degrade gracefully because they all `command -v … &> /dev/null` guard the calls, but the dependency should be declared so the package is self-contained. `wget` is listed in the installer's `REQUIRED_APT_PACKAGES` but is not used anywhere in `scripts/` — pure cruft.3.2 `debian/rules` (`debian/rules:1-58`)The rules file is minimal and correct:```makefile#!/usr/bin/make -f%:	dh $@override_dh_auto_install:	mkdir -p debian/ars-arcanum/usr/share/ars-arcanum/scripts/lib	…	cp -r scripts/* debian/ars-arcanum/usr/share/ars-arcanum/scripts/	find debian/ars-arcanum/usr/share/ars-arcanum -type d -name '__pycache__' -prune -exec rm -rf {} +	find debian/ars-arcanum/usr/share/ars-arcanum -type f \( -name '*.pyc' -o -name '*.pyo' \) -delete	chmod +x debian/ars-arcanum/usr/share/ars-arcanum/scripts/*.sh	chmod +x debian/ars-arcanum/usr/share/ars-arcanum/scripts/arcanum	…```Verified via `od -c` that all recipe lines start with a TAB character (not spaces) — this is the #1 silent killer of Makefile-based packaging and Ars Arcanum gets it right.Strengths:`dh $@` is the modern debhelper 13 idiom — the file is 13 lines of actual recipe and gets full `dh` sequencing for free.`override_dh_auto_install` rather than overriding `install` is the correct override point.The PKG-03 remediation that strips `__pycache__`, `*.pyc`, `*.pyo` (`debian/rules:17-18`) is essential for reproducible builds (Python byte-compiled artifacts embed timestamps and absolute paths).The PKG-02 launcher-substitution loop (`debian/rules:31-53`) is genuinely clever: rather than shipping `.desktop` files with a `__PROJECT_ROOT__` placeholder and hoping `setup_arcanum.sh` substitutes it (which the user-local installer does), the Debian package rewrites every known launcher to `Exec=/usr/bin/arcanum <subcommand>` at build time, then asserts via `! grep -r "__PROJECT_ROOT__" debian/ars-arcanum/usr/share/applications/` that no placeholder survived. Build-time fail-closed is the right pattern.Symlinks `debian/ars-arcanum/usr/bin/arcanum → /usr/share/ars-arcanum/scripts/arcanum` and `usr/bin/ars-arcanum → …/ars-arcanum` correctly expose the binaries on `$PATH` without copying them.Findings:Medium — no `debian/install`, `debian/links`, or `debian/docs` files. All install logic is inline in `debian/rules`. This is fine for a small package but means a future contributor can't review the file manifest without reading shell. Modern Debian style would push the `cp -r` into a `debian/ars-arcanum.install` file. Not a defect, just style.Low — no `debian/arcanum.manpages` or `debian/ars-arcanum.manpages`. The package ships no man pages. The `arcanum` script has a long `usage()` (`scripts/arcanum:29-104`) that would convert cleanly to `help2man`-generated man pages. For a Debian-sponsored package, `lintian` would flag `no-manpage-page` for each binary in `/usr/bin/`. Mint and Debian review boards prefer at least a stub man page.Low — `debian/rules` doesn't run `desktop-file-install` or call `dh_installmenu`. It just drops the `.desktop` files into `usr/share/applications/`. In practice this is fine because both `dh` and the desktop environments will auto-discover them, but using `dh_installdesktop` or running `desktop-file-install --dir=debian/ars-arcanum/usr/share/applications/` would set vendor prefixes and validate at build time.Info — the case statement at `debian/rules:33-45` hard-codes launcher filenames. If a future contributor adds an 11th launcher without updating the case, it falls through to the `else` branch and only the `__PROJECT_ROOT__` substitution happens. A grep-based fallback that infers the subcommand from the launcher's `Exec=bash __PROJECT_ROOT__/scripts/arcanum <args>` line would be more resilient.3.3 `debian/changelog` (`debian/changelog:1-9`)```ars-arcanum (1.6.0-1) unstable; urgency=medium  * Production readiness and modular architecture release.  * Packaged unified Python CLI dispatcher and plugin registry.  * Added atomic storage write safety, 3-way DOCX hash sync, and schema migrations.  * Hardened World Bible doctor, concordance back-matter engine, and diagnostics.  * Included FreeDesktop launcher specifications and headless GUI support. -- Aryan Singh Nagar <https://github.com/aryansinghnagar/Scriptorium>  Sun, 21 Sep 2026 12:00:00 +0530```Findings:Medium — wrong day-of-week. `date -d '2026-09-21' '+%A'` returns Monday, but the changelog says `Sun, 21 Sep 2026`. `lintian` will emit `W: changelog-weekday-mismatch`. Easy fix: regenerate with `dch --release` or hand-correct to `Mon`.Medium — malformed maintainer email (same as §3.1 — `https://github.com/...` is not an email).Low — single changelog entry. Real Debian packages have an entry per upload with multiple bullet points grouped by `* Added`, `* Changed`, `* Fixed`. The single entry is fine for a first upload but `lintian` will note `I: possible-missing-colon-in-closes` if Closes: lines are absent (which they should be for a project that references GitHub issues).Info — `unstable` distribution. Correct for an upload target. For a PPA, you'd use `~ppa1` suffix and `mantic`/`noble` distributions.3.4 `debian/copyright` (`debian/copyright:1-27`)```Format: https://www.debian.org/doc/packaging-manuals/copyright-format/1.0/Upstream-Name: ars-arcanumUpstream-Contact: Aryan Singh Nagar <https://github.com/aryansinghnagar/Scriptorium>Source: https://github.com/aryansinghnagar/ScriptoriumFiles: *Copyright: 2026 Ars Arcanum ContributorsLicense: MIT…```Strengths:Uses the canonical copyright-format 1.0 URL.Full MIT license text is reproduced verbatim (required for `debian/copyright`).`Files: *` is the correct catch-all.Findings:Medium — `Upstream-Contact` field has a URL in the email position (same as §3.1).Low — `Copyright: 2026 Ars Arcanum Contributors` is generic and forward-dated. The "Contributors" wording is acceptable but loses attribution granularity.Medium — no `Files-Excluded` field for vendored Obsidian plugins. The `templates/world-bible/.obsidian/plugins/*/main.js` files are ~2.4 MB each of third-party JavaScript. Debian's archive reviewers prefer these be documented with their own `Files:` stanza, separate upstream copyright, and license. As-is, the blanket `Files: *` claims MIT for code that is actually under each plugin's license (mostly MIT or AGPL — e.g., `longform` is MIT, `obsidian-git` is MIT, but `dataview` is MIT and `storyline` is MIT). Adding per-plugin license stanzas is a Debian review prerequisite.Low — no `Comment:` field describing the project. Optional but improves reviewability.3.5 `debian/source/format` (`debian/source/format:1`)```3.0 (native)```Correct format declaration. The choice of `native` (vs `3.0 (quilt)`) means there is no separate upstream tarball — the entire repo is the source package. This is the right choice for a self-contained project where the upstream maintainer and Debian maintainer are the same person. With `3.0 (quilt)`, the packager would need an `orig.tar.gz` plus a `debian.tar.xz`, which is unnecessary overhead here.3.6 Buildability assessmentThe auditor ran `dpkg-buildpackage --no-sign -us -uc -b -nc` in the sandbox. Flatpak Manifest Audit`org.arsarcanum.ArsArcanum.yaml` (66 lines).4.1 Runtime, SDK, and command```yamlapp-id: org.arsarcanum.ArsArcanumruntime: org.gnome.Platformruntime-version: '46'sdk: org.gnome.Sdkcommand: arcanum```Strengths:`org.gnome.Platform` 46 is a sensible LTS runtime choice (GNOME 46 was released March 2024). The runtime provides `glib`, `gtk3`, `gtk4`, `libadwaita`, `pygobject`, `python3` — all of which the project uses.Pinning `runtime-version: '46'` (a single major version) rather than `master` or `stable` is the correct pattern for reproducible builds.`command: arcanum` correctly points to the symlink installed at `/app/bin/arcanum` by the build-commands.Findings:High — `runtime-version: '46'` is already stale. GNOME 47 (Sept 2024), 48 (March 2025) are available. Flathub review recommends bumping within 6 months of a new LTS. Not blocking, but flagged.Info — could use `org.freedesktop.Platform` 24.08 instead. For an app that doesn't deeply depend on GNOME libraries (Ars Arcanum's GUI is GTK3/Libadwaita with Zenity fallback), the Freedesktop runtime is lighter (~250 MB vs ~700 MB for GNOME). Migration is straightforward.4.2 `finish-args` (sandbox permissions)```yamlfinish-args:  - --share=ipc  - --socket=fallback-x11  - --socket=wayland  - --socket=x11  - --filesystem=home  - --filesystem=xdg-desktop:ro  - --talk-name=org.freedesktop.Notifications```Findings:High — `--socket=fallback-x11` and `--socket=x11` are both declared. Per the Flatpak permission documentation, `fallback-x11` already provides X11 access only when Wayland isn't available. Adding `--socket=x11` forces unconditional X11 access, which weakens the sandbox and is flagged by `flatpak-builder-lint` as redundant. Remove `--socket=x1`.High — `--filesystem=home` is a sledgehammer. The comment at `org.arsarcanum.ArsArcanum.yaml:11-14` justifies it: "Ars Arcanum manages whole author trees (`~/Universes`, `~/Manuscripts`, `~/Worlds` legacy) plus Git metadata, so a scoped `home` grant replaces the two tilde grants." This is a defensible engineering choice — the previous version apparently used the deprecated `--filesystem=~/foo` tilde forms. However, `--filesystem=home` grants read-write to every file the user owns — SSH keys, `.bashrc`, `~/.config`, browser profiles, etc. — completely defeating the Flatpak sandbox. A tighter alternative: pre-create the three expected directories at first run and grant only `--filesystem=home/Universes --filesystem=home/Manuscripts --filesystem=home/Worlds --filesystem=home/.local/share/applications`. The project's own `setup_arcanum.sh:377-379` creates those three directories explicitly, so the manifest could rely on the same convention. Flathub reviewers will push back on `--filesystem=home` for any non-IDE app.Critical — `--talk-name=org.freedesktop.Flatpak` is missing. The `scripts/arcanum:345,358` dispatcher does:```bash  exec flatpak run io.gitlab.novelwriter.novelWriter "${NW_PROJ}"  …  exec flatpak run md.obsidian.Obsidian "${OBS_TARGET}"  ```Inside a Flatpak sandbox, calling `flatpak run` on another app requires the `org.freedesktop.Flatpak` D-Bus talk permission (and typically `--system-talk-name=org.freedesktop.Flatpak.System` for system installs). Without it, the `arcanum write` command will fail with `error: Failed to spawn child process "flatpak"`. The `control_center.sh:124,142` background launches are similarly broken. This means the Flatpak build of Ars Arcanum cannot open Obsidian or novelWriter from its Control Center, which is the headline feature of the project. Either add the talk permissions or restructure `arcanum write` to use `xdg-open` (which works through `xdg-desktop-portal` without extra permissions) and let the host system pick the right app for the file type.Medium — `--filesystem=xdg-desktop:ro` is half-solution. The installer writes launchers to the Desktop. Inside a Flatpak, the app shouldn't be writing to `~/Desktop` at all — desktop file export happens automatically via `flatpak-builder` when `.desktop` files are placed in `/app/share/applications/`. The manifest's `cp` of `.desktop` files into `/app/share/applications/` (line 55) already handles this; the runtime `--filesystem=xdg-desktop:ro` is dead weight.Medium — missing `--device=dri`. GTK3 + Libadwaita benefit from GPU acceleration. Without `--device=dri`, software rendering is forced, which makes the Control Center UI noticeably sluggish on Wayland. Add `--device=dri`.Medium — missing `--talk-name=org.freedesktop.secrets`. If the project ever integrates with keyrings (for, e.g., backup destination credentials), this is needed. Not currently used, so this is forward-looking.Info — `--share=ipc` is correct (required for X11 shared memory and Wayland surface sharing). `--socket=wayland` is correct. `--talk-name=org.freedesktop.Notifications` is correct for `notify-send` to work.4.3 Modules and `build-commands````yamlmodules:  - name: ars-arcanum    buildsystem: simple    build-commands:      - mkdir -p /app/share/ars-arcanum/scripts/lib      …      - cp -r scripts/* /app/share/ars-arcanum/scripts/      - find /app/share/ars-arcanum -type d -name '__pycache__' -prune -exec rm -rf {} +      - chmod +x /app/share/ars-arcanum/scripts/*.sh      …      - |        for f in launchers/*.desktop; do          …          sed -e "s|^Exec=.*|Exec=/app/bin/arcanum $sub|" …        done      - ln -s /app/share/ars-arcanum/scripts/arcanum /app/bin/arcanum      - ln -s /app/share/ars-arcanum/scripts/ars-arcanum /app/bin/ars-arcanum    sources:      - type: dir        path: .```Strengths:`buildsystem: simple` is correct — there's no autotools / meson / cmake.The build-commands mirror `debian/rules` exactly (same `__pycache__` stripping, same launcher substitution loop, same `chmod +x`, same symlink layout). This is good — both packaging paths produce functionally identical layouts.The multi-line YAML literal block (`- |`) for the launcher-substitution shell loop is syntactically valid.Findings:Critical — no Python runtime module. The `org.gnome.Sdk` provides Python at build time, but the `org.gnome.Platform` (which is what the runtime is) does not ship Python by default — only the SDK does. Per Flatpak best practice, runtime applications must bundle Python as a separate module if they need it at runtime. The project's `arcanum` dispatcher calls `python3 ${PROJECT_ROOT}/scripts/lib/*.py` for nearly every subcommand (`arcanum calc`, `arcanum codex`, `arcanum map`, `arcanum doctor`, etc.). Inside the Flatpak, `python3` will resolve to nothing — the build-commands install Python source files but no interpreter. The fix is either (a) add a `python3.json` module from the flatpak-builder-tools `python/flatpak-python-generator.py` workflow, or (b) use `org.gnome.Sdk//46` as the runtime (heavier but includes Python). As-is, the Flatpak is unusable for any Python-backed subcommand.Critical — no Typst / Pandoc / jq modules. The `export_book.sh` pipeline requires `typst`, `pandoc`, and `jq`. None are bundled in the Flatpak, and the sandbox cannot see host-installed copies. The Flatpak build of Ars Arcanum cannot compile a book. The standard fix is to add Flathub's shared-modules entries for `pandoc` (available) and to vendor `typst` as a `simple` buildsystem module that copies the musl binary from GitHub releases (the SHA-256 is already in `dependencies.lock:13-14`).High — no `cleanup` field. Best-practice Flatpak manifests strip `*.a`, `*.la`, `/share/man`, `/share/doc`, `/include`, etc. from the final image. Ars Arcanum's manifest has no `cleanup:` field. Impact is small because the manifest doesn't build any C/C++ libraries, but it's a Flathub review note.Medium — `sources: type: dir, path: .` ships the entire repo including `.git/`, `tests/`, `docs/`, `debian/`, `audit-reports/`. A cleaner approach is `type: archive` with a `dest` and a `skip` list, or `type: git` with a shallow clone. The current approach inflates the Flatpak bundle by ~5-10 MB of test fixtures and documentation.Low — `command: arcanum` lacks `desktop` and `icon` keys at top level. Modern Flatpak manifests support `desktop: org.arsarcanum.ArsArcanum.desktop` to bind a primary desktop file. Without it, Flathub shows the app under its app-id rather than a friendly name. The 10 launchers are present but none is the "primary" entry.4.4 Sandbox appropriateness verdictThe Flatpak manifest is structurally a Flatpak but functionally non-deployable. The auditor's verdict: the Flatpak would build (`flatpak-builder --user --install . org.arsarcanum.ArsArcanum.yaml`), the .desktop files would install, but clicking the launcher would fail at the first Python call and again at every `flatpak run` invocation. Installer / Uninstaller Audit11.1 `setup_arcanum.sh` idempotencyRe-running `setup_arcanum.sh` after a successful install:`apt-get update` + `apt-get install -y` are idempotent (apt skips already-installed packages).`flatpak_install()` at `setup_arcanum.sh:238-265` checks `flatpak info "$app_id"` first and skips if already present (`[✓] ${app_id} already present`).Typst block at `setup_arcanum.sh:305` checks `command -v typst` and skips download if already installed.`mkdir -p` is idempotent.`chmod +x` is idempotent.`ln -sf` (line 402-403) is idempotent (the `-f` forces overwrite).`gio set metadata::trusted true` is idempotent.The `cp` of `.desktop` files to `~/.local/share/applications/` and `~/Desktop/` overwrites silently.Verdict: idempotent. A user can re-run `setup_arcanum.sh` after every `git pull` to refresh the launchers and re-link the CLI.11.2 AtomicityThe installer is not atomic. It performs mutations in sequence without a rollback path:If `apt-get install` fails halfway, apt itself rolls back its own transaction, but the user is left with whatever flatpak installs already completed.If the Typst download fails, the script appends to `INSTALL_ERRORS` and continues to step 6 (desktop launchers), which still succeeds.The final summary at `setup_arcanum.sh:418-435` reports `[PARTIAL] Ars Arcanum setup finished WITH WARNINGS — Unresolved items:` and lists each error.This is a pragmatic compromise — true atomicity would require staging every mutation and committing atomically, which is infeasible for system package installs. The "collect errors and report at end" pattern is the right call.11.3 Rollback on failureThere is no automatic rollback. If the installer fails, the user is expected to either re-run it (idempotency helps) or manually run `uninstall_arcanum.sh` to clean up. The `INSTALL_ERRORS` array is the closest thing to a transaction log.Medium finding: the `INSTALL_ERRORS` array is populated but never causes the script to exit non-zero. At `setup_arcanum.sh:418-423`, the script prints `[PARTIAL] … WITH WARNINGS` and exits with whatever code `echo` returns (always 0). A CI system consuming this script cannot detect partial failure from the exit code. Fix: `if [ ${#INSTALL_ERRORS[@]} -gt 0 ]; then exit 1; fi` at the end.11.4 `uninstall_arcanum.sh` completenessVerified by reading every line:Removes all 11 desktop launcher files (10 launchers + 1 obsolete `scriptorium-control-center.desktop`) from both `~/Desktop` and `~/.local/share/applications/`. ✓Removes `~/.local/bin/arcanum` and `~/.local/bin/ars-arcanum` symlinks. ✓Removes `/usr/local/bin/typst` (with sudo, optional). ✓Optionally removes Flatpak apps (`--purge-flatpaks` flag). ✓Explicitly preserves `~/Universes`, `~/Manuscripts`, `~/Worlds` (line 154 confirms: "User writing data … remains intact and preserved").Findings:Medium — uninstaller does not call `update-desktop-database` or `gtk-update-icon-cache`. After removing the `.desktop` files, the desktop menu may show stale entries until the user logs out / logs in. Modern desktop environments auto-detect changes within seconds, so this is a polish issue, not a defect.Medium — uninstaller does not remove `~/.local/bin/typst` (the `--no-sudo` install path). Only `/usr/local/bin/typst` is removed. A user who installed with `--no-sudo` and then runs `uninstall_arcanum.sh` will have a leftover `~/.local/bin/typst`.Low — uninstaller does not remove `~/Universes`, `~/Manuscripts`, `~/Worlds` directories even if they are empty.
