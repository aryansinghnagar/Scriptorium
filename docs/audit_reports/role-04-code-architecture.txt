Role 04 — Code Architecture Analyst: Deep-Dive Audit of Scriptorium ("Ars Arcanum")> **Audit target:** `/home/z/my-project/scripts/scriptorium` (HEAD, v1.6.0)> **Audit date:** Single-pass deep dive> **Auditor mandate:** Structural design, layering, cohesion/coupling, Bash/Python boundary, domain modeling, abstractions, extensibility> **Method:** Direct file inspection, dependency-graph mapping via `rg`, function-level metrics, side-by-side diffing of duplicated routines> **Severity tags used:** Critical / High / Medium / Low / Info---1. Executive SummaryScriptorium/Ars Arcanum is a script-collection architecture masquerading as a modular monolith. From the outside it presents 50+ Python "engines," a 724-line Bash dispatcher (`scripts/arcanum`), a 3,873-line GTK 3 desktop app (`ui_gtk3.py`), an engine registry (`registry.py`), a UI controller (`ui_controller.py`), and 51 Python test files — the surface area strongly implies a layered, plugin-based system. Inside, the picture is different. There is no domain layer, no shared service layer, no interface abstractions, and the registry pattern exists but is never used for dispatch. The 34 KB Bash dispatcher is essentially a giant `case` statement of `exec python3 scripts/lib/<x>.py "$@"` calls; a parallel Python dispatcher (`scripts/lib/cli.py`) re-implements the same dispatch table but is reachable only via `arcanum engines`. Adding a new domain engine requires coordinated edits to four files (`scripts/arcanum`, `scripts/lib/cli.py`, `scripts/lib/registry.py`, and the new `scripts/lib/<x>.py`) — classic Shotgun Surgery.The strengths are real: zero external Python dependencies (pure stdlib), atomic file writes via a single `fs_utils.atomic_write`, a coherent domain ontology expressed in `templates/world-bible/Templates/fileClasses/`, a real plugin metadata registry with categories and aliases, a 7-stage test harness, a clean 4-value exit-code contract, and a strict `set -euo pipefail` Bash discipline. The weaknesses are equally real: 9 copies of `parse_yaml_frontmatter`, 9 copies of `resolve_world_dir`, 18 nearly-identical `generate_*_html_report` functions, a dead `ui_controller.py` (only its test imports it), a dead `load_engine_module` registry function, an enormous 3.8K-line god-GUI file, and `main()` functions of 100-184 lines that mix CLI parsing, business logic, IO, and presentation in every domain module.Overall verdict: C+. The codebase is honest, tested, and deployable, but its architecture is "flat collection of scripts" rather than "layered application," and the few abstractions it has (registry, controller, cli) are decorative rather than load-bearing. A focused 3-month refactoring effort — extracting a `core/` shared layer, wiring the registry into actual dispatch, and splitting `ui_gtk3.py` — would lift this to a B+ without changing user-facing behavior.---2. Architectural Style Assessment3.1 What style is this?The codebase exhibits features of three different architectural styles simultaneously, with none fully realized:Style	Evidence for	Evidence againstScript collection (Unix style)	Each `scripts/lib/<x>.py` is independently executable; bash dispatcher shells out via `exec python3 …`; no shared domain layer	Heavy shared infrastructure (`fs_utils`, `cache`, `config`, `registry`); a 3.8K-line GUI; presence of `__init__.py`-style import patternsLayered monolith	`docs/ARCHITECTURE.md` §3.3 lists five layers (Presentation / CLI Facade / Discovery / Workflow Engines / Storage); `ui_controller.py` exists to be a controller layer	No layer is enforced; domain modules import `argparse` and `print`; the "CLI Facade" duplicates the "Presentation Layer"; `ui_controller.py` is dead codePlugin-based / modular	`registry.py` defines `EngineSpec`, `EngineCategory`, aliases, `load_engine_module`; the README markets "Registered Plugins & Engines"	Registry is never used for dispatch; both dispatchers (bash + python) use hardcoded `case`/`if cmd in (...)` tables; no plugin discovery from filesystem; adding a plugin requires editing the registry by handVerdict: This is a script collection with layering aspirations and decorative plugin metadata. It works because the scripts are individually competent and the bash dispatcher is simple. It does not scale gracefully because every new feature repeats boilerplate that a real layering or plugin system would eliminate.3.2 Style stabilityThe 37 ADRs in `docs/ARCHITECTURE.md` show the team is acutely aware of architectural decisions and documents them carefully. ADR-012 ("Unified CLI Facade"), ADR-017 ("Unified Python GTK Desktop Control Center"), ADR-020 ("Shared Discovery Library & Fail-Closed Hardening"), and ADR-022 ("Separated Lore & Manuscript Architecture") show repeated attempts to impose structure. The fact that ADR-020 had to centralize discovery logic into `lib/worlds.sh` in 2024+ suggests the codebase has been reactive rather than designed up-front.---4. Bash/Python Boundary7.1 The 34 KB Bash dispatcher (`scripts/arcanum`)The file is 724 lines and breaks down as:Lines	Purpose1-27	Shebang, symlink resolution, `PROJECT_ROOT` discovery, version29-105	`usage()` — 76-line heredoc107-273	`interactive_menu()` — 166-line nested `case` of `read -p` + `exec`275-285	Default invocation → `interactive_menu` or `usage`287-723	Main dispatch `case "${COMMAND}"` — ~70 branches, each `exec python3 …` or `exec bash …`696-721	Unknown-command fallback: inline Python heredoc for typo suggestions via `difflib.get_close_matches`Justification assessment:The dispatch table itself is justified in bash. It is a list of `case "cmd") exec python3 .../lib/cmd.py "$@"` lines, which is the simplest possible glue and works fine. Converting this to Python would gain little.The 100-line `usage()` function is a maintenance liability. It must be hand-edited every time a command is added or an alias changes. It duplicates information already in `registry.py:_ENGINES` (`cli_command`, `aliases`, `title`, `description`). High severity — if the bash usage drifts from the registry, users see stale help.The 165-line `interactive_menu()` is unjustified in bash. It hardcodes English text, has nested `case` statements that duplicate the main dispatch table, and offers no advantage over a Python `curses`-based or `simple-term-menu`-based equivalent. Worse, the GUI (`arcanum_app.py`) already exists as a richer alternative — the bash menu is a third UI surface alongside CLI and GUI.The inline Python heredoc for typo suggestions is a code smell. It's a one-off 26-line Python script embedded in bash. It should be a small `scripts/lib/suggest.py` invoked as `python3 -m lib.suggest "$CMD"`.7.2 Duplicated dispatch tablesThere are two dispatchers:Bash (`scripts/arcanum:287-723`): ~70 case branches such as```basheconomy|economies|ppp)    exec python3 "${PROJECT_ROOT}/scripts/lib/economy.py" "$@"    ;;```Python (`scripts/lib/cli.py:111-254`): ~40 `if cmd in (...)` branches such as```pythonif cmd in ("economy", "currencies"):    return dispatch_subcommand("lib.economy", rest)```The Python `cli.py` dispatcher is only reachable from the bash dispatcher for the `engines` subcommand (`scripts/arcanum:661`: `exec python3 "${PROJECT_ROOT}/scripts/lib/cli.py" engines "$@"`). All other commands bypass `cli.py` entirely. Sample `world.yaml`:```yamlworld:  name: "sample_world"  universe: "SampleUniverse"  created: "2026-09-17"  type: "lore_vault"```But the lightweight YAML parsers in `cache.py:parse_frontmatter`, `factions.py:parse_yaml_frontmatter`, `economy.py:parse_yaml_frontmatter`, etc. all flatten keys and would parse this as `{"world": ""}` (empty value because the next line is indented). They cannot handle nested mappings. The only parser that handles nested YAML is `init_query.py`'s inline parser (lines 188-198), which is even simpler and also wouldn't handle nested keys.In practice this means: the manifests are read by humans and by `migrate.py`'s string-based `if "schema_version:" not in text` check, not by a real YAML parser. The Python modules that read manifests to extract business data (e.g. `calendar.py:144-154` reads `world.yaml`) get an empty dict back and fall through to defaults. This is a High-severity finding — the manifest schema is documented but not actually parsed.Critical — Zero PyYAML dependency means rolling 9 YAML parsers. The "zero external dependencies" stance (ADR-027, ADR-028) is principled but the cost is 9 copies of `parse_yaml_frontmatter` and an inability to handle the actual manifest schema. PyYAML is in Python stdlib adjacent (pure Python, widely deployed, < 200 KB) and would eliminate this entire class of problems.13.3 DOCX presets (in `config.py`)`config.py:103-152` defines `DOCX_PRESETS` dict with 4 presets (`standard-submission`, `modern-manuscript`, `classic-trade`, `custom`). This is hardcoded in Python — not in a config file. Low severity. A `configs/docx_presets.json` would let users add their own presets without code changes.13.4 `configs/idioms.json` and `configs/leechblock_arcanum_rules.json``idioms.json` is a 200+ entry dictionary of Earth-eponyms (`achilles heel`, `pyrrhic`, `draconian`, etc.) used by `idioms.py` to detect immersion-breaking real-world references in prose. It's loaded at module import time via `Path(__file__).parent.parent / "configs" / "idioms.json"`. Low severity — clean design.`leechblock_arcanum_rules.json` is a LeechBlock NG browser-extension config that blocks social/video sites during writing hours. It's not loaded by any Python code; it's a user-importable artifact. Info only.13.5 Template coherence`templates/world-bible/` contains 11 subdirectories (Characters, Locations, Factions, Economies, Bestiary, Artifacts, Cosmology, History, Languages, Magic-Technology, Templates) and 11 `fileClasses/*.md` Metadata Menu schemas. The templates match the fileClasses match the `type:` frontmatter values match the diagnostic code families.13.6 Configuration architecture scorecardAspect	Grade	NotesManifest schema clarity	B+	Well-documented in DEPRECATION.md, schema_version presentManifest parsing correctness	D	9 broken parsers that don't handle the actual schemaUser preference storage	A-	XDG-compliant, atomic writes, 0o600 permissionsDistractor blocklist	A	LeechBlock NG compatible, well-structuredTemplate coherence	A	11 entity types, 11 fileClasses, 11 directory templatesPreset extensibility	C	Hardcoded in Python; no user-overridable configCache coherence	A-	ANA-01 canonical count_words, mtime-keyed, healthy flag---14.
