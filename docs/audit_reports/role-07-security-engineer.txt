Executive SummaryArs Arcanum makes unusually strong, public security claims for a single-user Linux writing tool, and on the whole it backs them up with evidence rather than rhetoric. The codebase shows clear signs of security-conscious engineering: an explicit STRIDE-Lite threat model (`docs/THREAT_MODEL.md`), a per-module Content-Security-Policy baseline enforced by a CI test (`tests/test_threat_model.py:31-49`), zero `shell=True` / `os.system` / `eval` / `pickle` usage anywhere in the codebase, atomic writes via `os.replace` + `fsync` (`scripts/lib/fs_utils.py:12-65`), rigorous tar-member validation in `restore_world.sh:155-187` (rejecting absolute paths, `..` traversal, non-sample `.git/hooks/`, symlinks, hardlinks, FIFOs, device nodes), and a fail-closed SHA-256 verification gate for the downloaded Typst binary (`scripts/setup_arcanum.sh:312-327`). Secrets hygiene is clean — `.gitignore` excludes credential file patterns, the config file is written `0600` (`scripts/lib/config.py:88-93`), no tokens/API keys appear in any script, and Gitleaks runs on every push (`scripts/../.github/workflows/ci.yml:54-57`).However, the audit surfaced several gaps between the marketing claims and the actual implementation. (b) Backup archives are integrity-protected but NOT encrypted, so anyone who can read `~/Manuscripts/<ms>/05-Backups/*.tar.gz` obtains full manuscript prose. The code honestly discloses this limitation (`scripts/restore_world.sh:122-124`). (c) Dependabot is configured only for the `github-actions` ecosystem (`.github/dependabot.yml`), so version drift between `dependencies.lock`, the hardcoded `TYPST_PINNED_VERSION` in `setup_arcanum.sh`, and the `typst-version` pinned in `ci.yml` is not automatically detected. (d) The supply chain relies on trust-on-first-use of the installer script itself for the Typst SHA-256 — there is no out-of-band channel (cosign/sigstore/SLSA provenance) to verify the installer was not tampered with. (e) The CSP allows `script-src 'unsafe-inline'`, which is acceptable for offline-generated reports but weaker than a nonce-based policy.Verdict on the "fail-closed security" claim: PARTIALLY VERIFIED. The Typst binary digest gate, the restore-world archive validation, and the SHA-256 sidecar requirement are genuinely fail-closed. The `--book` argument handling in three scripts is not, and the backup archive confidentiality model is "fail-open" (reliance on filesystem permissions alone).Top strengths: atomic write infrastructure; tar-bomb/symlink/hook defense in restore; CSP enforcement via test; least-privilege CI workflow (`permissions: contents: read`); SHA-pinned third-party actions; honest disclosure of cryptographic limitations in inline comments.Top concerns: three scripts with unvalidated `--book` path components; unencrypted backup archives; absence of SLSA/sigstore provenance for the Typst binary; Dependabot coverage limited to GitHub Actions; no SAST tool beyond `ruff` (no `bandit`/`semgrep`).Overall grade: B+ (Strong, with clear, fixable gaps in defense-in-depth.)---2. Supply Chain Security4.1 Typst binary download and verification — VERIFIED (fail-closed)The installer downloads a pinned Typst musl binary from GitHub releases and gates installation on SHA-256 verification:```bash# scripts/setup_arcanum.sh:280-283TYPST_PINNED_VERSION="0.14.2"TYPST_SHA256_X86_64="a6044cbad2a954deb921167e257e120ac0a16b20339ec01121194ff9d394996d"TYPST_SHA256_AARCH64="491b101aa40a3a7ea82a3f8a6232cabb4e6a7e233810082e5ac812d43fdcd47a"```The verification logic (`scripts/setup_arcanum.sh:312-327`):```bashif curl -L -f -sS --retry 3 --connect-timeout 10 --max-time 60 -o "${TEMP_DIR}/typst.tar.xz" "${TYPST_URL}"; then    TYPST_OK=0    ACTUAL=$(sha256sum "${TEMP_DIR}/typst.tar.xz" | cut -d' ' -f1)    if [ -z "${EXPECTED_DIGEST}" ]; then        TYPST_OK=0        echo "  [!] Refusing to install unverified binary: upstream SHA-256 digest unavailable." >&2        INSTALL_ERRORS+=("Typst digest unavailable")    elif [ "${EXPECTED_DIGEST}" = "${ACTUAL}" ]; then        TYPST_OK=1        echo "  [✓] Typst tarball digest verified (sha256 ${ACTUAL:0:16}...)"    else        TYPST_OK=0        echo "  [!] Typst digest mismatch: expected ${EXPECTED_DIGEST}, got ${ACTUAL}. Aborting binary install." >&2        INSTALL_ERRORS+=("Typst digest mismatch")    fi```Strengths:Digest is computed over the downloaded `.tar.xz` archive, not the extracted binary — so any tampering with the inner binary would change the outer hash.Both mismatch and "digest unavailable" branches set `TYPST_OK=0` and refuse installation. The `sudo install -m 755` step at `:334` only runs when `TYPST_OK=1`. Genuinely fail-closed.`curl` is invoked with `-f` (fail on HTTP error), `-sS` (silent but show errors), `--retry 3`, `--connect-timeout 10`, `--max-time 60` — bounded network behavior, no indefinite hang.Both `x86_64` and `aarch64` architectures have pinned digests, and unsupported architectures fall through to a "build via cargo" advisory (`:296-299`) without installing anything.The pinned digest values are duplicated in `dependencies.lock:13-14`, providing a second source-of-truth for verification.Weaknesses:Trust-on-first-use of the installer script itself. The expected SHA-256 lives in the same script that downloads the binary. If an attacker can substitute `setup_arcanum.sh`, they can substitute the digest too. There is no out-of-band channel (cosign/sigstore/SLSA provenance, GPG-signed installer, separate `.sha256` file fetched from a different host). This is the standard limitation of curl|bash-style installers and is acceptable for the project's threat model, but it should be acknowledged.Digest pin is duplicated in two places (`setup_arcanum.sh:281-282` and `dependencies.lock:13-14`). Drift between them would not be detected automatically. Recommend a CI assertion that the two values match.No subresource-integrity verification for the extracted binary. The extracted `typst` binary is found via `find "${TEMP_DIR}" -type f -name "typst" | head -n 1` (`:331`) and installed. If GitHub's tarball were somehow signed-but-tampered (e.g., a release engineer's token was compromised but the hash published in `dependencies.lock` was somehow updated), there's no second check. In practice the outer-tar hash covers this.CI uses a different Typst installation path (`.github/workflows/ci.yml:39-43`: `typst-community/setup-typst@f97d94d65e19b033e103c69cb1f27b56dfbb040f # v4.0.1`) which has its own internal pinning. The pinned version `0.14.2` matches `dependencies.lock`, but the binary installed by the GitHub Action is not the same musl binary that `setup_arcanum.sh` installs locally — so CI tests run against a different binary than end users. This is acceptable for compiling `.typ` files (Typst is deterministic), but it means the SHA-256 verification is never exercised in CI.4.2 APT and Flatpak trust — PARTIALLY VERIFIEDAPT packages (`setup_arcanum.sh:140-154`, `:200`) are installed via `sudo apt-get install -y "${ALL_APT_CORE[@]}"` with explicitly named package lists and no wildcards — confirmed by reading the array definitions. Backup Security14.1 Backup creation — VERIFIED`scripts/backup_world.sh:159-228` creates a backup archive with three artifacts:`<project>-backup-<timestamp>.tar.gz` — gzip-compressed tarball of the project, with deterministic member order (`--sort=name`), neutralized ownership (`--owner=0 --group=0 --numeric-owner`), and excluded backup/exports/cache directories (`:183-191`).`<project>-backup-<timestamp>.sha256` — `sha256sum` output sidecar, immediately verified via `sha256sum -c` (`:224-228`).`<project>-backup-<timestamp>.meta.json` — JSON metadata with `world`, `timestamp`, `archive`, `sha256`, `size_bytes`, `git_commit` (HEAD SHA at backup time), and `note`. Written via Python `json.dump` (`:209-223`).Strengths:Pre-flight free-space check (`:170-176`) compares source size vs destination available bytes and aborts on insufficient space.Dual-target replication to a user-configured secure external destination (`:236-252`) with second `sha256sum -c` verification after copy.Deterministic tarball (`--sort=name`, `--owner=0 --group=0 --numeric-owner`) makes backups reproducible and diff-able.Backup archive is never included in itself (excludes `05-Backups/` and `Backups/`).14.2 Finding M-3 (Medium): Backup archives are NOT encryptedThe threat model's "Threat T3: Backup Archive Tampering" mitigation (`docs/THREAT_MODEL.md:53-54`) claims: "Every archive generation emits a companion `.sha256` digest sidecar verified before any restoration drill." This is accurate for integrity, but the threat model does not address confidentiality. The `.tar.gz` archive is uncompressed-then-gzip'd plain Markdown — anyone with read access to `~/Manuscripts/<ms>/05-Backups/*.tar.gz` (or the secure external destination) obtains the full manuscript prose, world lore, and character notes.The code honestly discloses this in `restore_world.sh:122-124`:> Note: .git/hooks/*.sample files ship with every 'git init' and appear in every legitimate Ars Arcanum backup; only non-sample hooks (which would execute on the next snapshot commit) are rejected. The co-located sha256 manifest proves integrity against bit-rot, not authenticity: anyone who can replace the archive can regenerate the manifest.But the disclosure is in the restore script, not in `backup_world.sh` or the threat model. Recommendation:Add a `--encrypt` flag to `backup_world.sh` that pipes the tarball through `gpg --symmetric --cipher-algo AES256` (or `age`) before writing. The SHA-256 sidecar would then cover the encrypted archive.Document in `SECURITY.md` and `PRIVACY.md` that backups are integrity-protected but not confidentiality-protected by default, and recommend LUKS for the external drive.The README already recommends LUKS full-disk encryption (`README.md` data-safety section) and Déjà Dup for external backups — but `backup_world.sh` itself does not integrate with these.14.3 Restore path — VERIFIED, fail-closed`scripts/restore_world.sh:108-132`:```bashif [ -f "${SHA_FILE}" ]; then    echo "[i] Verifying SHA-256 checksum against ${SHA_FILE}..."    (        cd "${ARCHIVE_DIR}"        if ! sha256sum -c "${BASE_NAME}.sha256" >/dev/null 2>&1; then            echo "[!] ERROR: SHA-256 Checksum verification failed! Refusing to restore without integrity verification." >&2        echo "If you trust this archive, re-run with --skip-checksum (or --force)." >&2        exit 1    fifi```Default behavior: refuse to restore if the `.sha256` sidecar is missing. This is the strongest interpretation of the README's "fail-closed security posture" claim, and it is correctly implemented.14.4 Restore drill testing`scripts/verify.sh` (referenced in README as the "7-stage automated health check") is documented to include "backup/restore drills".
