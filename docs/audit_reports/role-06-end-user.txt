Executive SummaryAfter two days of reading every user-facing surface — the 22 KB `README.md`, the 1,113-line `docs/AUTHOR_MANUAL.md`, the four `init_*.sh` wizards, the templates, the sample fixtures, the ten `.desktop` launchers, and the export/backup/concordance scripts — my honest verdict is: I would adopt Ars Arcanum, but cautiously, and only as my second tool alongside a flat Markdown fallback. This is a project whose philosophy (sovereign Markdown, zero telemetry, no vendor lock-in, plain files on my disk) is exactly right for me, whose execution is more thoughtful than 95% of open-source writing tools I have tried, but whose daily-driver polish is still beta-grade in ways that would burn a non-technical author within the first week.Top delights. The Typst book template (`templates/typst/book_template.typ`) is genuinely publication-grade: alternating gutter margins, half-title + full title + copyright + dedication + epigraph, verso author / recto title running headers, ornamental `✦ ✦ ✦` scene breaks, body pagination restarting at 1. The transactional staging in `init_world.sh:227-312` (mktemp → atomic mv → cleanup trap) is the kind of safety I expect from a paid product. The dual-target SHA-256 verified backup (`backup_world.sh:179-228`) and the restore engine's refusal to extract symlinks, traversal members, or non-sample git hooks (`restore_world.sh:155-187`) mean I can actually trust a USB drive in a drawer for three years. The `00_START_HERE.md` lore-vault guide explicitly tells me worldbuilding is procrastination ("You do not need to fill out all 9 lore categories before you start writing") — that is the voice of someone who has met writers before.Top frustrations. The README and Author Manual disagree on whether the Control Center has five tabs or six studios (`README.md:116` vs `docs/AUTHOR_MANUAL.md:116` vs `docs/START_HERE.md:21` vs `CHANGELOG.md` M27). The promised "starter cosmos with pre-configured lore and starter chapters" (`README.md:82`) does not appear to ship in the repo — the only samples I found are the skeletal `tests/fixtures/sample_*` (a 22-line character file, a 6-line universe, two chapters of ~15 lines each). There is no Scrivener/Word manuscript importer despite the README mentioning "migration" repeatedly. The continuity engine's death-detection regex (`series_continuity.py:38-41`) only catches the verbs `died|was slain|perished|succumbed|fell in battle|was executed|breathed their last` — anyone who kills a character with "his sword found her heart" will silently resurrect her in book 5. And accessibility is barely addressed: hardcoded pastel redline colors with ~1.4:1 contrast, no documented keyboard accelerators in the GTK app, and zero mention of the word "accessibility" in the README.Grade: B−. Adopt for the philosophy and the publication toolchain, but keep a `tar.gz` of my manuscripts somewhere I control, and budget two weeks of friction before the workflow feels native.---2. First-Run Experience — `setup_arcanum.sh`I read the README's Quick Start (`README.md:66-83`) and the installer in full. The promise is: clone the repo, run one command, get a working studio. The reality is closer to: clone, run one command, wait 20-45 minutes, then troubleshoot Flatpak on hotel Wi-Fi.What the installer does well. OS gating is honest (`setup_arcanum.sh:99-125`): Mint 21/22 and Debian 12/13 pass; anything else must use `--force`. `--dry-run` actually creates no files (not even the log file — see the careful comment at `setup_arcanum.sh:52-63`). `--no-sudo` lets me preview without root. The Typst install pins v0.14.2 with a hardcoded SHA-256 (`setup_arcanum.sh:280-282`) and refuses to install if the digest mismatches (`setup_arcanum.sh:323-327`). Failures are aggregated into `INSTALL_ERRORS` and `FLATPAK_FAILED` arrays (`setup_arcanum.sh:236-272`) and printed honestly at the end, instead of papering over a missing Obsidian with a green `[✓]`. This is better than most installers I have used.What will go wrong for a real user.Time. APT update + 30 packages (5-10 min on a fresh Mint), 7 font packages (1-2 min), Flathub remote add, then three Flatpak app installs: Obsidian (~150 MB + GNOME runtime ~600 MB if not present), novelWriter (~30 MB), Calibre (~300 MB + KDE runtime if not present). On a 5-year-old ThinkPad with average home Wi-Fi, the first install realistically runs 25-40 minutes. On hotel/cafe Wi-Fi the curl Typst download has `--connect-timeout 10 --max-time 60` (`setup_arcanum.sh:312`) which is sensible, but the Flatpak installs have no such timeout and can hang for 10 minutes on a stalled CDN. Severity: Medium — the installer will eventually succeed, but a non-technical author who panics and Ctrl-C's it will be left in a half-installed state with no resume capability.`gio set metadata::trusted true` does not actually trust launchers on modern XFCE. Line 408-411 of `setup_arcanum.sh`:```   for df in "${DESKTOP_DIR}/"*.desktop; do       [ -f "$df" ] && gio set "$df" metadata::trusted true 2>/dev/null || true   done   ```On Linux Mint 22 XFCE with the default `thunar` and `xfdesktop`, freshly created `.desktop` files in `~/Desktop` still require right-click → "Allow Launching" the first time, regardless of `gio` metadata. The `2>/dev/null || true` swallows the failure silently. So a new user who double-clicks "Ars Arcanum Control Center" on the desktop gets the "Untrusted application launcher" dialog and has no idea what to do. Severity: High — this is the literal first click of the daily workflow and it breaks. The README does not mention this.The "Next Steps" message is misleading. `setup_arcanum.sh:439-444` tells me to "Double-click 'New World Vault Creator' … to start a lore vault" and "Double-click 'New Manuscript Creator' … to start a novel." But these launcher names don't match the actual `.desktop` files — the launchers are named "New World Vault Creator" (`launchers/init-world.desktop:4`) and there is no "New Manuscript Creator" launcher named exactly that; `launchers/init-manuscript.desktop:4` is "New Manuscript Creator" ✓. Actually that one does match. The naming is fine. But: the user is told to start a World Vault before a Universe, and the docs elsewhere say Universes contain Worlds. The onboarding order is ambiguous. Severity: Low.Sudo prompt mid-install with no warning. `sudo -v` is checked at `setup_arcanum.sh:128-137` but only after OS detection. The first time a non-technical user sees a password prompt, they may believe something is wrong. The installer prints `[1/6] Updating package repositories...` immediately before the first `sudo apt-get update` (`setup_arcanum.sh:192`), with no heads-up that a password is coming. Severity: Low.No uninstall verification. `uninstall_arcanum.sh` is referenced in `SECURITY.md` and `PRIVACY.md` but I did not test it. The README does not walk me through "if you want to remove Ars Arcanum, do this." A privacy-conscious user like me wants to know the exit before I enter.Total time estimate for a successful first install on a fresh Mint 22: 25-40 minutes including OS gating, APT, fonts, Flatpaks, and Typst. Add 15 minutes for the inevitable XFCE "Allow Launching" dance and the first Control Center launch.---5. Initial Wizard / Scaffolding — the four `init_*.sh` scripts`init_universe.sh` (185 lines)This is the thinnest wizard of the four. It sanitizes the name (`init_universe.sh:95`), creates `universe.yaml` (8 lines), `Universe-Index.md` (~20 lines), `.gitignore` (4 lines), and runs `git init` + initial commit. The default name suggested in the zenity dialog is `"Default-Universe"` (`init_universe.sh:81`), which is the dullest possible name for a narrative cosmos. A more evocative default like `"My-Cosmos"` or simply forcing the user to type one would set a better tone.The Universe-Index.md it generates is essentially a placeholder: a title, two metadata lines, and a paragraph of boilerplate ending with "Open any individual world folder as a dedicated Obsidian vault." There are no next-step instructions, no link to the Author Manual, no example. A user who creates a universe and then closes the dialog has no idea what to do next. Severity: Medium — the entry point to the whole system is also its emptiest room.`init_world.sh` (344 lines)This is where the project starts to feel serious. The transactional staging architecture (`init_world.sh:227-312`) is the right shape: `STAGING_DIR=$(mktemp -d)`, a `trap cleanup EXIT INT TERM` that only fires if `SUCCESS=0`, all ten lore category directories created up front (`init_world.sh:239-249`), templates copied in via `cp -a` (`init_world.sh:252-254`), validation checks that each required directory exists (`init_world.sh:286-289`), and only then an atomic `mv` into place (`init_world.sh:311`). If anything fails mid-staging, the destination directory is never touched. This is exactly how I would want a paid product to behave.The zenity flow (`init_world.sh:88-128`) offers a list of existing universes with a "+ Create New Universe" option — sensible. The completion dialog (`init_world.sh:334`) tells me how to open the vault in Obsidian and which plugins are pre-configured. Good.Issues:Documentation mismatch. `init_world.sh:239-249` creates 10 directories: Characters, Locations, Factions, Economies, Magic-Technology, Bestiary, Artifacts, Cosmology/Prophecies, History, Languages, Templates/fileClasses. But `docs/AUTHOR_MANUAL.md:186` says "The 9 Core Lore Vaults" and the table that follows lists 9 rows. Economies is the missing one in the docs. Severity: Low — but it makes me distrust the docs.The `arcanum.yaml` "backwards compatibility" manifest (`init_world.sh:278-283`) is created alongside `world.yaml` with overlapping fields. When I open the vault in a text editor and see both files, I will not know which one is authoritative. Severity: Low for daily use, but confusing for power users.No prompt for description or author. `world.yaml` gets `description: "World Lore Vault for ${WORLD_NAME}"` (`init_world.sh:275`) — a useless placeholder. The user is never asked "what is this world about?" Severity: Low but a missed onboarding opportunity.`init_manuscript.sh` (319 lines)Same transactional staging pattern. Creates `Book-01/{01_Act_I,02_Act_II,03_Act_III}`, `Outlines/`, `Exports/`, `Backups/`. Copies the manuscript templates (4 sample chapters, Master-Outline, Subplot-Thread-Matrix, `nwProject.nwx`). Generates `nwProject.nwx` with proper XML escaping (`init_manuscript.sh:163-179`) and validates it immediately with `python3 -c 'import xml.etree.ElementTree as ET; ET.parse(...)'` (`init_manuscript.sh:207-212`) — fail-closed if malformed. This is the right discipline.Issues:Default author is `"Author Name"` (`init_manuscript.sh:90`). This propagates into `manuscript.yaml`, `arcanum.yaml`, `nwProject.nwx`, and the eventual PDF copyright page (`book_template.typ:103`). If I forget to override it on init, every PDF I export will say "Copyright © 2026 by Author Name." The user is never prompted to set their real name during scaffolding. Severity: High — a single forgetful moment produces embarrassing artifacts.DOCX auto-build is silent. `init_manuscript.sh:297-299` runs `docx_sync.py build` after the atomic move, but pipes stderr to `/dev/null` and `|| true`. If the build fails, I will not know until I try to open the `.docx` in Word and find it missing or empty. Severity: Medium.`.gitignore` excludes `Exports/` and `04-Publishing/` (`init_manuscript.sh:229-231`). This means my exported PDFs are NOT version controlled. If I want to recover an old PDF, I cannot use Git — I have to re-export from the Markdown source. That is a defensible design choice (binaries bloat Git), but it should be documented prominently. Severity: Low.`init_draft.sh` (307 lines) — the dangerous oneThis script forks a new draft (Draft-02, Draft-03) from an existing one. The logic at `init_draft.sh:202-219` is the problem: if the manuscript was scaffolded by `init_manuscript.sh`, the chapters live directly in `Book-01/01_Act_I/01_Chapter_01.md` (flat structure). The first time I run `init_draft.sh`, it detects this flat structure and "Establishes discrete 'Draft-01' baseline folder from existing scenes" by copying the flat structure into `Book-01/Draft-01/` (`init_draft.sh:204-219`). Then it copies again into `Book-01/Draft-02/`.But it never removes the originals from `Book-01/01_Act_I/`. After forking Draft-02, I now have three copies of my chapters: the original flat `Book-01/01_Act_I/01_Chapter_01.md`, `Book-01/Draft-01/01_Act_I/01_Chapter_01.md`, and `Book-01/Draft-02/01_Act_I/01_Chapter_01.md`. The `manuscript.yaml` `active_draft` pointer is set to Draft-02, so the export engine uses Draft-02. But the flat-structure originals are still there, will still be picked up by `find` commands that don't filter Draft-*, and will be a source of confusion forever. The wordcount script (`wordcount_report.sh`) explicitly handles this in newer versions per the changelog ("gracefully parse multi-draft directory hierarchies ... while preserving flat hierarchy compatibility") — so the count won't double. But the files are still on disk, and a user browsing in a file manager will see duplicate chapters with no explanation. Severity: High — this is a foot-gun that will cause real confusion the first time a user forks a draft.Recommendation: After the baseline migration copy, the script should move the originals into `Book-01/Draft-01/` (atomic rename) instead of copying, then leave a `.baseline-migrated` marker file in `Book-01/` so the user knows the flat structure is gone.---6. Daily Writing Workflow — Friction AuditLet me walk through a real writing day with Ars Arcanum as the README and Author Manual describe it.Open a chapter. I double-click "Ars Arcanum Control Center" (after right-clicking and "Allow Launching" because XFCE's trust mechanism didn't take). The GTK app launches. I go to Tab 2 (or is it Studio 2? — the docs disagree). I see my manuscript in the selector. The Manuscript Tree Explorer shows `Book-01 → 01_Act_I → 01_Chapter_01.md`. I click it. The Visual Scene Metadata Inspector shows `@pov:`, `@location:`, `@status:`. I click "Open in Word Processor" — LibreOffice Writer opens with `Draft-01_Manuscript.docx` (the consolidated draft, not the individual chapter — that's a friction point if I want to focus on one chapter). Friction: 2 clicks + LibreOffice launch (~5 sec). Acceptable.Write. I write 800 words in LibreOffice. I save with Ctrl+S. The `.docx` mtime updates. LibreOffice does not touch the `.md` file. So far, so good.Sync `.docx` back to Markdown. I click "🔄 Sync DOCX ↔ Markdown" in the Control Center. This runs `arcanum docx sync` which calls `scripts/lib/docx_sync.py`. The sync engine compares mtime and SHA-256 state in `.sync_state.json` (`docs/THREAT_MODEL.md:51`). If both files diverged independently, it branches to `<chapter>.conflict_<timestamp>.md` instead of overwriting. This is correct, safe behavior. But: if I forget to click Sync before I close LibreOffice and then re-open the chapter from the Control Center, I will see the old Markdown prose, not my 800 new words. The disconnect will panic me. Friction: I must remember to click Sync before closing the word processor. The system does not enforce or remind me. Severity: Medium — this is exactly the kind of cognitive overhead a "zero terminal" tool is supposed to eliminate.Run wordcount. Click "Words & Analytics" or run `arcanum words`. The cache engine (`scripts/lib/cache.py`) makes this sub-second on large manuscripts. Good. The `--pov` flag gives me POV screen-time balance. Excellent. The starvation alert (>3 chapters without a POV appearance) is a feature I would actually use. Friction: zero.Save snapshot. Click "📷 Quick Snapshot" in the top bar. A zenity entry dialog asks for a note. I type "Wrote chapter 7 battle scene, ~1500 words." Git commits across world + manuscript repos. `notify-send` confirms. Friction: 3 clicks + typing a note. Excellent. Caveat: `save_snapshot.sh:184-197` snapshots discrete `Book-*/` repositories if they exist, but only if the user has run `init_draft.sh` to create them. The flat `Book-01/01_Act_I/...` structure created by `init_manuscript.sh` is not a discrete Git repo — only the manuscript root is. So on a fresh manuscript, snapshots work but they are coarse-grained (whole-manuscript commits, not per-book). Severity: Low.Total friction for one writing session: ~7 clicks, one sync step I must remember, one snapshot. That is acceptable for a sovereign local-first tool, but it is not the frictionless "open and write" promised by `docs/AUTHOR_MANUAL.md:6` ("Zero programming or terminal experience is required for daily writing. Everything is accessible through the Ars Arcanum Control Center desktop app"). It is closer to "everything is accessible from the desktop app, but you must remember the sync ritual." Severity: Medium — the promise oversells the reality.---8. Worldbuilding Workflow — Adding EntitiesAdding a character. Open the World Lore Vault in Obsidian (1 click from Control Center). Concordance & Continuity — Does It Actually Catch Errors?I tested this by reading `tests/test_continuity_engine.sh` and `tests/fixtures/sample_world/`. The honest answer: yes, it catches a useful subset of errors, but the regex coverage is narrow enough that I cannot rely on it as my only continuity safety net.Concordance (`generate_concordance.sh` + `scripts/lib/concordance.py`). Parses YAML frontmatter from `Characters/`, `Languages/`, `Bestiary/`, `Artifacts/`, `Factions/` and generates `04_Back_Matter/01_Dramatis_Personae.md` and `02_Glossary_and_Concordance.md`. These are auto-compiled at the end of Typst PDFs by virtue of alphabetical folder ordering (`04_Back_Matter/`). I read the frontmatter parser (`concordance.py:35-90`) — it handles flat key-value, list-with-dashes, and inline `[a, b, c]` lists. It cleans wikilinks via regex. It extracts a quote (`> ...`) or summary section from each note body. This is solid.What it does not do: It does not extract character mentions from the manuscript prose itself — it only reads the World Bible dossiers. So if I introduce "Lord Valerius" in chapter 3 of the manuscript but never create a dossier for him, he will not appear in the Dramatis Personae. The concordance is lore-driven, not prose-driven. Severity: Medium — a real Dramatis Personae should reflect who actually appears in the book, not just who has a dossier.Single-book continuity (`scripts/lib/continuity.py`). I read the trait patterns (`continuity.py:32-58`). It extracts `eye_color`, `hair_color`, `status`, `title` from World Bible frontmatter AND from manuscript prose via regex. The `TRAIT_PATTERNS` dict covers:Eye colors: blue, green, hazel, brown, dark, amber, grey, gray, violet, golden, black, crimson, emerald, sapphire (14 colors).Hair colors: black, raven, dark, blonde, blond, golden, brown, auburn, red, silver, white, grey, gray (13 colors).The test `test_continuity_engine.sh:46-76` proves it catches a Vaelor with brown eyes described as "bright blue eyes" in a later scene → CNT-101 fires. This works. But:It misses scars, height, build, handedness, voice, accent, age, tattoos, distinctive features — all of which the character template explicitly asks for. If I describe Kaelen as left-handed in book 1 and right-handed in book 4, no warning fires.It misses name aliases. If a character is introduced as "the Witch of the Marches" in book 1 and named "Maren" in book 3, no continuity check bridges them unless I add `aliases: [Witch of the Marches]` in frontmatter — and even then, the continuity engine does not appear to consult the `aliases` field in prose matching.Series continuity (`scripts/lib/series_continuity.py`). This is the one I most wanted to love, because my 7-book epic has deaths, resurrections, and aging to track. I read the entity extractor (`series_continuity.py:38-110`). It extracts:Eye/hair colors via the pattern `\b([A-Z][a-zA-Z]{1,20})\b[^\.\n]{0,50}\b(?:had|with|of)\s+([a-z]+)\s+eyes\b`. This requires "Name had/with/of COLOR eyes" — exact phrasing. If I write "Kaelen's blue eyes narrowed," the regex does not match because the name and color are split by possessive `'s`. Severity: High — most fiction does not use "Name had blue eyes" phrasing.Deaths via `DEATH_PATTERNS`: `died|was slain|perished|succumbed|fell in battle|was executed|breathed their last` and `the death of NAME`. This misses: "killed", "murdered", "stabbed", "drowned", "burned alive", "his sword found her heart", "she crumpled", "the light left his eyes", "no breath remained". Severity: High — for a 7-book series where poetic deaths are common, the engine will silently miss the majority of death events and then fail to catch resurrections.Characters via `@pov:` and via `\b([A-Z][a-z]{2,15})\s+(?:said|asked|shouted|whispered|cried|replied|thought|stepped|drew|smiled|nodded|commanded|looked|turned|stood|fought|advanced)\b`. This produces many false positives — any capitalized word at the start of a sentence followed by "looked" or "turned" or "stood" gets extracted as a character. "Suddenly stood the watchman" → "Suddenly" gets extracted. The filter list excludes common adverbs (He, She, They, It, There, When, Then, After, Before, While, Suddenly, Finally, Soon, Now) but misses "Quietly", "Slowly", "Gently", "Softly", "Once", "Perhaps", "Maybe", "Sometimes". Severity: High — running this on a 150-character epic will produce hundreds of false character entries, drowning real continuity errors in noise.Continuity verdict: C+. The idea is right, the execution is regex-naive. A real novelist cannot rely on this as the only continuity safety net. I would use it as a supplement to manual reading, not a replacement.Recommendation: Either (a) document explicitly that the continuity engine is best-effort and produces false positives/negatives, or (b) upgrade to a proper NLP approach (spaCy entity recognition is offline and FOSS). Option (a) is cheaper.---10. Export & Publishing — PDF / EPUB / DOCX Quality`export_book.sh` (621 lines) is the largest user-facing script and the one I most looked forward to. Backup & Recovery — Can I Sleep at Night?This is the section I most needed to be confident in, and largely I am. Verdict: B+.What works.`backup_world.sh` creates a `.tar.gz` + `.sha256` sidecar + `.meta.json` (with git commit hash, timestamp, size, note) — verified locally and (if configured) replicated to a USB destination with second-side checksum verification (`backup_world.sh:179-228`). Includes `.git` history so disaster recovery preserves version history. Pre-flight free-space check (`backup_world.sh:171-176`). Deterministic archive order via `--sort=name` and numeric owner (`backup_world.sh:181-182`). Uses Python `tarfile` to reject symlinks, hardlinks, FIFOs, device nodes, absolute paths, and `..` traversal members before extraction (`restore_world.sh:155-187`). Rejects non-sample git hooks to prevent code execution on the next commit (`restore_world.sh:170-173`). Atomic swap on `--force` overwrite with `.bak` rollback (`restore_world.sh:264-278`). Destination must be inside `$HOME` or `/tmp`/`/var/tmp` (`restore_world.sh:210-228`).This is the most thoughtful backup/restore I have seen in a writing tool, paid or free.What does not work / is missing.No `--list` flag on restore. I cannot inspect what is in an archive before restoring it. If I have 12 backup archives in `~/Manuscripts/My-Novel/Backups/` and want to know which one has the version of chapter 7 from March, I have to extract them all manually with `tar -tzf`. Severity: Medium.No restore drill / dry-run. The README says "Test full system recovery with `arcanum restore`" (`README.md:182`) but does not explain how to test without overwriting. I would have to use `--dest /tmp/drill` and then manually clean up. A `--dry-run` flag that just verifies checksums and lists what would be restored would give me real confidence. Severity: Medium.No automatic scheduled backups. The 3-2-1 backup story is entirely manual. I must remember to click "Create Standalone Backup Archive" in the Control Center. The Obsidian Git plugin auto-commits every 10 minutes for the World Bible, but that is Git history, not a standalone archive. If my disk dies between Git commits, I lose up to 10 minutes of world-bible work and all uncommitted manuscript work since the last manual snapshot. Severity: High — for a tool whose marketing emphasizes data safety, the lack of cron-able or systemd-timer-able scheduled archives is a real gap.No backup verification after creation. `backup_world.sh:225-228` runs `sha256sum -c` after archive creation, which is good. But it does not extract the archive to a temp dir and verify the files match the source. A bit-rot scenario where tar wrote garbage that nonetheless checksum-matches its own (garbage) content would pass. Severity: Low (paranoid).No backup retention policy. Every backup creates a new timestamped archive. After a year of daily backups, I have 365 archives taking up significant space, with no auto-pruning. I must manually delete old ones. Severity: Low.Backup verdict: B+. I would sleep at night with this, but I would also schedule a recurring calendar reminder to click "Backup" weekly, and I would test-restore into `/tmp` monthly.---12. Severity: High for any migrating user.What does not exist.No Scrivener `.scriv` importer. Scrivener stores content as `.rtf`/`.txt`/`.md` files inside a `.scriv` package with a `.scrivx` project manifest. A parser could read the binder and reconstruct the chapter tree. None exists.No plain-`.docx`-to-ars-arcanum batch converter. A user with a 100,000-word novel in a single `.docx` has no way to chunk it into chapters automatically.No Markdown-folder importer. No `docs/MIGRATING_FROM_SCRIVENER.md`, no `docs/IMPORTING_WORD_MANUSCRIPTS.md`, no `docs/COMING_FROM_NOVELWRITER.md`.Migration verdict: D. The `migrate.py` script is misnamed — it should be `upgrade_schema.py`. The `docx import` command exists but is one-chapter-at-a-time. For a project that promises "sovereign, no vendor lock-in," the absence of a real migration path into the system is a significant gap.Recommendation: Write `docs/MIGRATION_GUIDE.md` with worked examples for Scrivener (compile to multi-file `.docx`, then loop `arcanum docx import`), Word (split by Heading 1, then import each), novelWriter (the `.nwx` is already supported — but how do I bring in an existing `.nwx` project?), and plain Markdown folders. Multi-Volume Series Support — Does It Actually Scale to 7 Books?The README and Author Manual mention "Book-01, Book-02" repeatedly. The series continuity engine (`series_continuity.py`) exists. The export supports omnibus (`--book all`). The `add_book.sh` script scaffolds new volumes. So far, so good.What works at 7-book scale.Scaffolding. `arcanum add-book My-Manuscript Book-07` creates `Book-07/{01_Act_I, 02_Act_II, 03_Act_III}` + starter chapters + discrete Git repo. ✓Discrete Git repos per book. Each `Book-XX/` has its own `.git/`, so I can commit to Book-07 without touching Book-01. ✓Omnibus export. `arcanum export --book all` compiles all 7 books into a single PDF/EPUB. ✓Per-book DOCX. Each book's draft has its own `Draft-01_Manuscript.docx`. ✓What does not work at 7-book scale.Series Bible template. As noted in §6, there is no template for an overarching series bible — a single file tracking prophecy fulfillment across 7 books, foreshadowing planted in book 1 that pays off in book 6, character arc throughlines, the timeline of the whole epic. The `Subplot-Thread-Matrix.md` is per-manuscript, not per-series. Severity: High for epic authors.Series continuity engine limitations. As detailed in §9, the death-detection regex misses most poetic deaths, and the character-extraction regex produces many false positives on capitalized sentence-starters. For 150 named characters across 7 books, the noise will drown the signal. Severity: High.Cross-book character tracking without IDs. Characters are identified by display name (regex match). If I rename "Kaelen" to "Kael" in book 4 (a character growth moment), the engine treats them as two separate characters. There is no character UUID system. Severity: Medium.No series-level wordcount. `arcanum words` reports per-manuscript. There is no `arcanum words --series` that totals all 7 books. The portfolio dashboard (`arcanum portfolio`) aggregates but at a coarse project level, not a series level. Severity: Low.No series-level plot matrix. The plot matrix (`arcanum plot`) is per-manuscript. I cannot see how the A-plot of book 1 connects to the B-plot of book 5. Severity: Medium.Timeline coordination. The `@time: 1899-03-14` tag anchors scenes to in-world dates, but there is no series-level timeline visualization showing all 7 books' events on a single chronological axis. The Calendarium plugin handles in-world calendars within a single vault, but not cross-book. Severity: Medium.Multi-volume verdict: C+. The scaffolding works. The continuity engine's regex limitations become acute at series scale. The absence of a series bible template is the biggest gap. I would use this for a trilogy; for my 7-book epic, I would need to build my own series-bible structure in Obsidian and not rely on the built-in continuity checker.---19.
