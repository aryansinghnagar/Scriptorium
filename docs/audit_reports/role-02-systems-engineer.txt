Executive SummaryArs Arcanum ("Scriptorium") is a deliberately over-engineered, single-user, local-first authoring orchestration layer that stitches together seven external tools (Git, Pandoc, Typst, Obsidian, novelWriter, Calibre, LibreOffice) over a three-tier Markdown + YAML + `.docx` file hierarchy. From a systems-engineering standpoint it is a surprisingly mature beta: every long-lived script honours a 4-value exit contract, atomic file writes are centralized in `scripts/lib/fs_utils.py:12`, scaffolding operations stage to `mktemp -d` and trap-cleanup (`init_world.sh:229-236`, `init_manuscript.sh:136-143`, `restore_world.sh:134-144`), the GTK UI pushes long-running work to daemon threads (`ui_gtk3.py:3593-3594`), the cache engine uses mtime+size invalidation with bounded reads (`lib/cache.py:39, 195-249`), and the backup/restore pipeline validates SHA-256 manifests and refuses non-regular archive members (`restore_world.sh:155-187`).However, the system carries the typical pathology of a Bash/Python hybrid orchestrator that grew organically: a multi-tier Git hierarchy that uses `git add` on embedded repos without submodule plumbing, manifest schemas that diverge between init scripts and test fixtures, a DOCX 3-way sync whose `.sync_state.json` is tracked by Git (so it merges-conflicts across machines), a per-project `.gitignore` that omits the runtime `.arcanum_cache.json` (despite the CHANGELOG claiming otherwise), and a CLI dispatcher that swallows subprocess exit codes via `2>/dev/null || true` in several init branches. There is no central lock manager; the only concurrency control is a 12×0.5 s poll on `.git/index.lock` (`save_snapshot.sh:147-156`), which works for the intended single-author workflow but breaks down the moment an author opens Obsidian Git's 10-minute auto-commit and clicks "Quick Snapshot" and runs `arcanum export` simultaneously.Top strengths: atomic-write primitive, transactional scaffolding with trap cleanup, dual-target SHA-256 backups with path-traversal refusal, mtime-keyed cache with truncation flags, structured diagnostic logging with path redaction (`lib/diagnostics.py`), fail-closed dry-run installer (`setup_arcanum.sh:52-63`).Top concerns: multi-tier embedded-repo Git pattern is fragile (no `.gitmodules`, parent tracks only gitlink SHA), DOCX sync state is committed rather than ephemeral, per-project `.gitignore` omits cache files, no global subprocess timeout policy in shell scripts (only the Python UI layer enforces timeouts), the `arcanum` interactive menu uses `read -r -p` without `-t` (will hang forever in a broken terminal), and the verify harness reuses a single sandboxed `$HOME` for an entire lifecycle pass that creates three Git repos and two tar archives inside `mktemp -d` with no size cap.Overall grade: B+ (Solid beta; production-ready for the documented single-author Linux-Mint/Debian target; would be C+ for any concurrent/multi-user scenario, which is explicitly out of scope per ADR-001).---2. Hierarchy soundnessThe four-level `Universe → World → Manuscript → Book → Draft → Chapter` hierarchy is logically clean and the `manuscript.yaml` `universe:`/`world:` linkage (`init_manuscript.sh:237-245`) decouples prose from lore cleanly (ADR-022). However, the file-system hierarchy does not match the Git-repository hierarchy, which is the single largest architectural smell:A Universe repo contains a `git add .` of its world directories (`init_world.sh:315-323`), but each World has already been `git init`-ed as its own repo (`init_world.sh:293-307`). The universe repo therefore commits gitlinks (mode 160000) to the world repos, not their content. The `git config advice.addEmbeddedRepo false` invocation at `init_world.sh:297` only suppresses the warning; it does not turn the child into a submodule.The same pattern repeats at Manuscript → Book (`init_manuscript.sh:276-285`) and at Manuscript → Volume (`add_book.sh:214-225`).No `.gitmodules` file is ever written. The parent repository stores only a SHA-1 commit pointer. If the child repository is ever lost, moved, or rebased, the parent commit becomes a dangling reference with no recovery path. `git submodule update --init` cannot rescue it because the modules file does not exist.This is documented in ADR-013 as "complete narrative isolation, modular scaling" but is technically a misuse of the embedded-repo pattern. A correct implementation would either (a) skip per-tier Git entirely and use a single repo with subtree path-based tagging, (b) use real Git submodules with `.gitmodules`, or (c) use Git subtrees. The current "gitlink without submodule" pattern is a known sharp edge that the Git project itself documents as fragile (gitlinks without `.gitmodules` are unrecoverable if the child history is lost).3.3 CouplingCoupling between subsystems is moderate but unidirectional and well-structured:`lib/worlds.sh` is the canonical discovery library, sourced by 14 scripts; idempotent guard at line 33-37 prevents double-source.The CLI facade (`scripts/arcanum`) is a pure dispatcher; it `exec`s into per-task scripts without sharing mutable state.The GTK UI (`ui_gtk3.py`) talks to the same shell scripts via `subprocess.run` — there is no Python↔Bash shared memory or socket IPC, which keeps the contract clean but means every UI action forks a 200 ms+ Python+Bash startup.The Python lib modules share a common pattern: each tries `from lib.fs_utils import atomic_write`, then `from fs_utils import atomic_write`, then defines a non-atomic fallback. 30+ modules duplicate this exact 14-line import block verbatim (verified via grep on `atomic_write`). This is a DRY violation; a single `lib/compat.py` shim would eliminate the boilerplate.3.4 VersioningManifest schema version is `"1.0"` everywhere (`init_world.sh:271`, `init_manuscript.sh:239`, `init_universe.sh:116`), and `lib/migrate.py:26` carries `CURRENT_SCHEMA_VERSION = "1.0"`. The migration engine upgrades legacy `scriptorium.yaml` → `world.yaml` and adds `schema_version:` headers (`migrate.py:46-110`). However, the test fixtures use a completely different schema — `tests/fixtures/sample_manuscript/manuscript.yaml` nests keys under a `manuscript:` root dict (`manuscript: { title: ... }`), while `init_manuscript.sh:237-245` writes flat top-level keys (`title: ...`). The runtime manifest readers (`export_book.sh:161`, `generate_concordance.sh:136`, `world_doctor.sh:126`) all use `sed -n -E 's/^title:[[:space:]]*"?…/'` which expects flat keys — so the fixture's nested manifest would never parse correctly at runtime. This is Info (test-only) but signals that the migration contract is not test-enforced end-to-end.---4. But it never sets `GIT_COMMITTER_DATE` or uses `--date`, so commit timestamps are wall-clock. This is fine for single-user but means two machines running `arcanum save` near-simultaneously produce commits with colliding SHA-1s only if every other field also collides (essentially impossible), so no practical issue.4.4 AtomicityThe `atomic_write` primitive in `lib/fs_utils.py:12-65` is textbook-correct:`tempfile.mkstemp` in the same directory as the target (ensures same filesystem for `os.replace`).`os.fdopen(fd) → write → flush → os.fsync(fileno)`.Preserve permissions of existing target via `os.chmod(tmp_path, target.stat().st_mode & 0o7777)`.`os.replace(tmp_path, target)` — atomic on POSIX.`os.fsync(dfd)` on the parent directory to flush the rename.Cleanup temp file in `except BaseException` (catches KeyboardInterrupt too).Verified by `tests/test_atomic_write.py` (5 tests, including temp-file cleanup). The `tests/test_cache.py:73-80` further verifies the resulting file gets mode `0o600` (because `mkstemp` creates with 0600 and `os.replace` preserves that). This is one of the strongest parts of the codebase.4.5 Race conditionsThe only file-level concurrency control in the entire system is the `wait_for_git_lock()` poll in `save_snapshot.sh:147-156`:```bashwait_for_git_lock() {    local repo_dir="${1:-.}"    local lock_file="${repo_dir}/.git/index.lock"    local attempts=0    while [ -f "${lock_file}" ] && [ $attempts -lt 12 ]; do        sleep 0.5        attempts=$((attempts + 1))    done}```This polls every 500 ms for up to 6 seconds, then proceeds regardless of whether the lock is still held. If Obsidian Git's auto-commit (10-min interval per `templates/world-bible/.obsidian/plugins/obsidian-git/data.json`) is mid-flight when the author clicks Quick Snapshot, the snapshot's `git add -A` at line 215 will fail with `index.lock` contention. The script does NOT retry the actual `git add` — it just proceeds to `git_commit_safe` which will also fail, and the script exits with `[!] Snapshot failed: git commit rejected the change.` at line 228. Medium severity.There is no `flock` anywhere in the codebase (grep confirmed). The `.sync_state.json` writes are not guarded by any lock; if two `arcanum docx sync` invocations ran simultaneously (e.g., user clicked the button twice rapidly), both would `load_sync_state → mutate → save_sync_state` and the second write wins. Low severity in practice because the GTK UI disables the button during sync.---5. Process & Lifecycle Analysis5.1 Subprocess orchestration patternsThe codebase uses three distinct subprocess invocation idioms:Pattern A — Fire-and-forget detached launch (`ui_gtk3.py:3614-3637`, `docx_sync.py:807-817`): `subprocess.Popen(argv, stdout=DEVNULL, stderr=DEVNULL, stdin=DEVNULL, start_new_session=True)` followed by a daemon thread that `proc.wait(timeout=30)` and logs failures. Correctly prevents zombies via `start_new_session=True` + reaper thread. Excellent.Pattern B — Stream-to-UI worker (`ui_gtk3.py:1924-1930, 3140-3148`): `subprocess.Popen(cmd, stdout=PIPE, stderr=STDOUT, text=True)` + `_stream_process_to_log` reader thread + `proc.wait()`. No timeout on the wait — if the child hangs (e.g., Typst stuck on a corrupt font), the worker thread blocks forever, the UI's progress bar pulses forever, and the user has no way to cancel. Medium severity. Compare with `_run_dialog_cmd` at line 2110 which does use `subprocess.run(timeout=120)`.Pattern C — Synchronous subprocess.run with timeout (`ui_gtk3.py:1495, 2110, 2142, 3114, 3124, 3158-3160, 3168, 3641`): timeouts ranging from 5 s (version probes) to 120 s (long exports). `TimeoutExpired` is caught and surfaced to the status bar. Good.The shell scripts themselves (e.g., `export_book.sh`, `backup_world.sh`) invoke `typst`, `pandoc`, `git`, `tar` without any `timeout` wrapper. A stuck Typst compile would hang the parent script indefinitely, and because `set -e` is in effect, `set -e` does NOT rescue you from a hanging subprocess (it only triggers on non-zero exit). The only place shell-level timeouts appear is `setup_arcanum.sh:312` where `curl --connect-timeout 10 --max-time 60` bounds the Typst download. Medium severity.5.2 Signal handlingTrap-based cleanup is consistently applied:Script	Trap	Coverage`init_world.sh:236`	`trap cleanup EXIT INT TERM`	Staging dir removed on any exit`init_manuscript.sh:143`	`trap cleanup EXIT INT TERM`	Same`restore_world.sh:144`	`trap cleanup EXIT INT TERM`	Staging dir removed`export_book.sh:192`	`trap 'rm -rf "${TEMP_WORK_DIR:-}"' EXIT`	Temp compile dir removed`verify.sh:46`	`trap cleanup EXIT`	Sandbox `$HOME` + tmpdir removed`setup_arcanum.sh:308, 350`	`trap 'rm -rf "${TEMP_DIR:-}"' EXIT` then `trap - EXIT`	Typst download dirInconsistency: `init_world.sh` and `init_manuscript.sh` register traps for `EXIT INT TERM` but not for `HUP`. Low severity.The `cleanup` functions in `init_world.sh:231-235` and `init_manuscript.sh:138-142` use a `SUCCESS` flag that is only set to `1` after the final `mv` succeeds — meaning on success the staging dir is NOT cleaned up, but it has already been moved away (the `mv` is the success signal), so there's nothing to clean. The logic is correct but subtle. Info.5.3 Exit propagationThe 4-value exit-code contract (`0` success, `1` runtime failure, `2` usage error, `3` user abort) is documented in `CONTRIBUTING.md:24-37` and consistently enforced. The CLI dispatcher at `scripts/arcanum` uses `exec bash ...` for every subcommand, which propagates the child's exit code directly to the parent shell — correct.However, the GTK UI's `_run_async_command` at `ui_gtk3.py:3639-3650` does:```pythondef _run_async_command(self, cmd, success_msg, callback=None, timeout=120):    try:        res = subprocess.run(cmd, capture_output=True, text=True, timeout=timeout)    except subprocess.TimeoutExpired:        GLib.idle_add(self.set_status, "Error: command timed out.")        return    if res.returncode == 0:        GLib.idle_add(self.set_status, success_msg)    else:        GLib.idle_add(self.set_status, f"Error: {res.stderr.strip() or 'Command failed'}")    if callback:        GLib.idle_add(callback)```The `callback` runs regardless of success or failure. So `on_quick_snapshot_clicked` → `_run_async_command(cmd, "...", self.refresh_snapshot_history)` will refresh the snapshot history list even when the snapshot failed — the user sees no new snapshot but no error indication either (only the status bar shows it). Failure Modes & Resilience6.1 Partial-failure scenariosI traced the following partial-failure scenarios through the code:Scenario A — Disk full during `tar -czf` in `backup_world.sh:179`. The `tar` command will fail mid-stream, leaving a partial `.tar.gz` at the destination. The script then checks `[ ! -s "${ARCHIVE_TAR}" ]` at line 194 — but a partial tar is non-empty, so this check passes. The `sha256sum` then runs on the partial archive and writes a `.sha256` sidecar. The user is presented with "[✓] Primary backup archive created and verified" even though the archive is corrupt. The follow-up `sha256sum -c` at line 227 will pass because it's verifying the partial archive against its own freshly-computed hash. High severity — the verification is self-referential. A correct implementation would (a) compare tar exit code, (b) check tar's `--checkpoint` notifications, or (c) verify the archive with `tar -tzf` listing after creation.Scenario B — Network failure during Typst download in `setup_arcanum.sh:312`. `curl -f -sS --retry 3 --connect-timeout 10 --max-time 60` fails → `TYPST_OK=0` → `INSTALL_ERRORS+=("Typst download failed")` → script continues to install launchers and finishes with `[PARTIAL]` summary. Good — the failure is captured but not fatal. The author can re-run setup later.Scenario C — Typst digest mismatch (`setup_arcanum.sh:323-326`). Refuses to install, records error, continues. Excellent fail-closed posture.Scenario D — Pandoc EPUB failure mid-export (`export_book.sh:528-541`). `EXIT_STATUS=1` is set, error log is shown, PDF/DOCX exports still proceed. This is the AUD-02 "independent error trapping" pattern documented in ADR-011. Excellent.Scenario E — Typst compile failure during export (`export_book.sh:478-491`). Same pattern: `EXIT_STATUS=1`, error log saved to `${PUBLISHING_DIR}/typst_compile_err.log`, EPUB/DOCX proceed. The final `exit "${EXIT_STATUS}"` at line 621 propagates the failure to the caller. Excellent.Scenario F — `git add -A` fails due to `index.lock` contention (`save_snapshot.sh:215`). Under `set -e`, this would abort the script. But there's no `|| true` here. Looking again: `wait_for_git_lock "."` is called at line 214 before `git add -A`. If the lock is still held after 12×0.5 s, the `git add -A` will fail with non-zero, and `set -e` aborts the script. The author sees no error message because the failure is in a non-interactive context. Medium severity — should `|| { echo "..."; exit 1; }` to give an actionable error.Scenario G — Restore of an archive that contains a non-sample `.git/hooks/post-checkout` (`restore_world.sh:170-173`). Refuses extraction with `Error: archive contains non-sample .git/hooks members; refusing extraction (code-execution risk).` Excellent — security-hardened.Scenario H — Restore archive contains a symlink (`restore_world.sh:175-187`). Same pattern.`backup_world.sh`: each invocation creates a timestamped archive; idempotent by design.`save_snapshot.sh:217-225`: if `git diff --cached --quiet` (no changes), prints message and `exit 0`. Performance & Caching8.1 Cache architecture`lib/cache.py` implements an mtime-keyed JSON cache:```python# cache.py:213-225cached_entry = files_cache.get(rel_path)if (    not cached_entry    or cached_entry.get("mtime") != stat.st_mtime    or cached_entry.get("size") != stat.st_size):    parsed = parse_markdown_file(md_path)    files_cache[rel_path] = parsed    ...    updated = True```Invalidate on mtime OR size change. Correct and standard. Caveats:mtime resolution on most Linux filesystems is 1 ns (btrfs/ext4) but only 1 s on FAT32. If an author backs up to a FAT32 USB and edits there, mtime collisions are possible. Acceptable for the Linux-native target.mtime can be spoofed by `touch -r`. If an attacker (or a sync tool like Syncthing) sets mtime back, the cache serves stale data. Low severity — single-user system, threat model is "crash recovery" not "adversary".The cache file itself is not in the per-project `.gitignore` (only in the repo root `.gitignore`, which doesn't apply to `~/Universes/...`). This means `arcanum cache scan` followed by `arcanum save` will commit the cache file to the world's Git repo, bloating history and causing merge conflicts when the same project is opened from two machines. Medium severity. The CHANGELOG at line 215 claims this was hardened, but I verified by reading `init_world.sh:257-267` and `init_manuscript.sh:221-231` — neither `.gitignore` template includes `.arcanum_cache.json` or `*.arcanum_cache.json`. The CHANGELOG claim is incorrect.8.2 Cache invalidationTested by `tests/test_performance_cache.sh:74-89` (Test 3): write file, scan, append text, rescan, assert word count increased. Good coverage.`tests/test_performance_cache.sh:91-112` (Test 4) verifies that `world_doctor.sh --fast` produces identical output to `world_doctor.sh` (standard) by stripping the cache-observability fields and asserting equality. Excellent — fast-path correctness is enforced.8.3 UI-level caches`ui_gtk3.py:131-135` defines three module-level caches:`_world_lore_counts: dict` keyed by `(world_path, mtime)` (OPT-03).`_dialog_cache: dict` keyed by method name (OPT-07) — singleton dialog reuse.`_git_history_cache: dict` keyed by `(wpath_str, head_mtime)` (OPT-08).The `_git_history_cache` is invalidated by `git_dir/HEAD` mtime, which is updated by every commit/checkout. Correct.`_cached_which()` at `ui_gtk3.py:91-100` caches `shutil.which()` results and is flushed by `_flush_tool_cache()` before every doctor run (OPT-04). Good — avoids 4 syscalls × N tools on every refresh.8.4 BottlenecksStartup time. `arcanum_app.py` → `ui_gtk3.py` → GTK window construction (3873-line UI file, 6 tabs, dozens of widgets). Acceptable.Engine dialog generation. Each speculative engine (astrophysics, genealogy, etc.) launches `python3 scripts/lib/<engine>.py` as a fresh subprocess — 100-200 ms Python startup + actual work. Low severity — exports are infrequent.---9. Medium severity for disaster recovery posture.9.2 Integrity verification`backup_world.sh:199-228`:```bashACTUAL_SHA="$(sha256sum "${ARCHIVE_TAR}" | cut -d' ' -f1)"echo "${ACTUAL_SHA}  ${ARCHIVE_BASE}.tar.gz" > "${CHECKSUM_FILE}"...(    cd "${PRIMARY_BACKUP_DIR}"    sha256sum -c "${ARCHIVE_BASE}.sha256" >/dev/null)```This is self-referential as noted in §6.1 Scenario A — the SHA-256 is computed from the (possibly corrupt) archive and then "verified" against itself. A real integrity check would either (a) hash the source tree separately and compare, or (b) `tar -tzf` the archive to verify it's a valid tarball. The current approach catches bit rot (the file on disk changed) but not creation-time corruption (the file was corrupt when written). Medium severity.The dual-target replication at `backup_world.sh:237-252` copies the archive + checksum + meta to a second destination and re-runs `sha256sum -c` there. This catches transport corruption (e.g., USB write errors). Excellent — better than most consumer backup tools.`restore_world.sh:108-132` enforces fail-closed: missing `.sha256` sidecar → refuse to restore unless `--skip-checksum` or `--force`. Excellent.9.3 Restore testing`verify.sh:474-490` (Stage 6j) runs a full backup → restore drill:`backup_world.sh --world "${WORLD}"` creates archive + `.sha256`.Asserts archive exists and `.sha256` exists.`restore_world.sh --archive "${BACKUP_ARCHIVE}" --target "${RESTORE_TARGET}" --universe "${UNIVERSE}"`.Asserts `${RESTORED_PATH}/Characters` exists.Asserts `${RESTORED_PATH}/Characters/Aethelgard.md` exists.Excellent — this is genuine restore-test discipline, not just "the archive was created". Many production systems skip this step. However, the drill only verifies that one character file is present after restore. It does not verify:Git history is preserved (`git -C restored log --oneline | wc -l`).Other lore files are present.The `.obsidian/` plugin configs are intact.The `world.yaml` manifest is intact.Low severity — should expand the restore assertions.9.4 Off-hostThe README and `BACKUP_SETUP.md` recommend:Déjà Dup for automated encrypted backups to USB/cloud (out of scope for Ars Arcanum).Dual-target replication via `arcanum backup-dest set /media/usb/backups` → `arcanum backup <target>` replicates to both local `Backups/` and the configured external destination (`backup_world.sh:137-150, 237-252`).There is no native cloud-sync integration (no S3, no rsync.net, no Backblaze). Closing NotesScriptorium is the rare Bash/Python project that takes operational discipline seriously: a 4-value exit contract enforced across 22 shell scripts, an atomic-write primitive used by 30+ modules, transactional scaffolding with trap cleanup, a genuine backup-restore drill in CI, and fail-closed security on archive extraction. The architecture documentation (35 ADRs, C4 diagrams, confidence assessment table) is more rigorous than most enterprise systems.The chief liabilities are: (1) the multi-tier Git pattern uses embedded gitlinks without `.gitmodules`, making child-history loss unrecoverable; (2) backup SHA-256 verification is self-referential and misses creation-time corruption; (3) concurrency control is a single 6-second poll, not a real lock; (4) per-project `.gitignore` templates don't match the CHANGELOG's claims about cache exclusion; (5) shell scripts bypass the structured logger that the Python layer uses, creating an observability gap.All identified issues are fixable within a single quarter by one engineer. The Phase 1 hardening items (F-02, F-03, F-04, F-05, F-09) are individually small and would close the most operationally dangerous gaps. The Phase 2 submodule migration (F-01) is the largest single investment and would transform the project from "robust for single-author" to "robust for team / multi-machine".End of report.
